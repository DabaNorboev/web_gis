# Ревизия checker ORS — 26.10.2026

**Статус: завершено.** [План](REVISION-PLAN.md) выполнен на сохранённых ответах.
Ложные отказы из-за представления геометрии устранены для части маршрутов без
собственного fork ORS. Это не интеграция нового provider и не подтверждение
реальной доступности выбранных мест.

## Выполненная последовательность

1. Закреплены исходные состояния Git, 427 tracked-файлов и 13 файлов прежнего
   эксперимента, 12 входов: выборка, PBF, контекст, препятствия, узлы, ответы и
   прежние reviews/runtime. Использован новый каталог свидетельств.
2. Независимый аудит разделил требования к представлению, доступу и препятствиям.
   Подтвердил ложные отказы одного-сегментного matcher, геометрической группировки
   проекций и жёсткого запрета по имени кейса. Реальные конфликты railway сохранены.
3. Добавлены отдельные `source_chain.py`, `endpoint_groups.py`, `revision_review.py`.
   Исторические `historical_review.py`, `review_ors.py`, policy и первый отчёт
   не переписаны. Существующее приложение не менялось.
4. До прогона фиксированной выборки прошли 53 синтетических проверки. Независимый
   review выявил дефекты нового кода; они исправлены с регрессиями. Итог — 58 тестов.
5. Повторно оценены все 11 пар в двух режимах. После исправлений выполнен отдельный
   заключительный прогон в `final/`; предварительные выводы сохранены отдельно.
6. Независимо повторены опасные случаи, проверены исходные входы и сохранность.
   Следующий продуктовый этап автоматически не начат.

## Что изменилось в проверке

| Было | Стало |
|---|---|
| Отрезок ответа обязан совпасть с одним исходным ребром | Восстанавливается однозначная цепочка исходных рёбер заявленного ORS way |
| Совпадающие координаты могли подменять связь сети | Переход требует общего исходного OSM node ID; близость сама не соединяет дороги |
| Пропущенная вершина давала отказ | Пропущенные вершины восстановлены и проверяются вместе с промежуточными узлами |
| Доступ проверялся также по геометрически совпавшим сторонним дорогам | Доступ и направление проверяются только на установленной исходной цепочке |
| Две проекции у одного узла могли считаться разными дорожными выборами | Они группируются по одному общему исходному узлу в прежней полосе 1 м |
| Кейсы bridge/railway не могли стать положительными по имени | Решение зависит от текущих рёбер, препятствий и доказательств уровней/пересечения |
| Препятствия проверялись на упрощённых отрезках | Проверяются восстановленные исходные рёбра и отдельно соединители концов |

Точность концов 0,25 м и радиусы 20/35 м сохранены. Отдельный параметр 1,25 м
ограничивает **только отклонение формы** упрощённого отрезка от исходной цепочки:
1 м закреплённого импортного упрощения плюс 0,25 м точности представления.
Он не разрешает проход через препятствия и не используется для выбора соседнего
way. Если нельзя однозначно восстановить цепочку, результат не принимается.

У самопересечений/замкнутых ways проверяются возможные цепочки; неоднозначность
сохраняется. Частичные концы не присваивают непройденные узлы маршруту. Сбой в
середине линии не стирает независимо установленную опасность соединителя у конца.
Для будущего интерфейса согласованной геометрией является восстановленная
исходная цепочка: сырой упрощённый shape не получает автоматически подтверждения
отсутствия пересечения с каждым препятствием на карте.

## Окончательные результаты

`Согласован` ниже означает только `MODEL_GEOMETRY_CONSISTENT` с сохранённым
неполным источником. Пользовательские расстояние/ETA в обоих reviews остаются
null. Это не оценка покрытия города, качества интерфейса или реального прохода.

|---|---|---|
| centre | Неоднозначность → недостаточно данных: пеший доступ на trunk не установлен | Недостаточно данных → согласован |
| solnechny | Требует уточнения → тот же отказ привязки до 20 м | Недостаточно данных → согласован |
| right_bank | Недостаточно данных → согласован | Недостаточно данных → согласован |
| bridge | Недостаточно данных → согласован | Недостаточно данных → не установлены уровни железнодорожных пересечений |
| railway | Недостаточно данных → сохранились стены/уровни и неполное сопоставление | Недостаточно данных → сохранились уровни и неполное сопоставление |
| quantum | Неоднозначность → неподтверждённые indoor/conveying участки | Требует уточнения → сохранился неподтверждённый соединитель; цепочка неполная |

| building_centre | Требует уточнения → внутри здания | Требует уточнения → внутри здания |
| edge_building | Требует уточнения → внутри здания | Требует уточнения → внутри здания |
| outside_pilot | Вне пилота → вне пилота | Вне пилота → вне пилота |

Изменились статусы 8 из 22 результатов. С исходной моделью согласованы три пеших
примера (right_bank, bridge, hotel) вместо одного и три автомобильных примера
(centre, solnechny, right_bank) вместо нуля. Среди пяти прежних обычных пар это
2/5 пешком и 3/5 автомобилем — исторический минимум 4/5 не достигнут, новый Go
по старой методике не объявляется. При этом доля от всей выборки, включающей
отрицательные контроли, не является полезным показателем городского покрытия.

В подтверждённых примерах максимальное восстановленное отклонение формы —
0,833 м для пешего right_bank, 0,730 м для пешего bridge, 1,016 м для автомобильного
solnechny. Все промежуточные исходные рёбра сохраняются в JSON для проверки;
они не отбрасываются ради совпадения ответа движка.

### Что по-прежнему не доказано

- Для railway остаётся несовместимость части концов с точностью 0,25 м; для
  автомобильного quantum есть часть цепочки вне допуска формы, stadium —
  несопоставленный конец. Это ограничения текущего способа сопоставления,
  сами по себе не доказательство ошибочного маршрута ORS. Независимые известные
  проблемы соединителей/препятствий при этом не скрыты.
- Пешая политика для крупных дорог и indoor/conveying не менялась. Centre
  проходит по trunk без подтверждённых пеших условий; quantum содержит indoor.
  Их превращение в успех потребовало бы отдельного предметного решения.
- Отсутствующий слой пересекаемой железной дороги/ограды не заменён доказанным
  разделением уровней. Переезд/ворота разрешаются только по относящемуся к пути
  общему исходному узлу и подходящим тегам доступа.
- Автомобильные relation turn restrictions этим offline checker независимо не
  проверяются; в каждом car-результате явно `NOT_VALIDATED`. Положительный статус
  не равен полному контракту текущего OSRM provider.
- Входы, реальная проходимость, дата наблюдения, время поездки и пользовательская
  пригодность не проверены. Новых маршрутов/матриц/изохрон не запрашивали.

## Независимая проверка и регрессии

В review исправлены:

- разрешение многометрового движения вдоль стены или railway по одному общему
  gate/level_crossing: узел теперь разрешает только точечное пересечение;
- смешение доказательств для объекта одновременно railway и fence: каждому
  препятствию нужно отдельное основание;
- падение на HTTP 200 с несловарным телом;
- утрата известного опасного соединителя при несопоставленной середине линии.

Независимый повтор подтвердил исправления, а также сохранность проверок
пройденных узлов на частичных рёбрах. Дополнительных блокирующих замечаний не
найдено. Это review экспериментального checker, не независимый аудит всего продукта.

58 тестов включают цепочки и замкнутые ways, одинаковые координаты разных IDs,
параллельные дороги, узловую неоднозначность без транзитивного слияния, короткие
запрещённые участки, односторонность, убранный из ответа закрытый gate, стену и
здание на исходном изгибе, неподтверждённый слой, ошибки ответа и очистку старого
драйвера. Тесты целевые, без БД/контейнеров/сети. Python AST, локальные ссылки,
`git diff --check` и повторяемость заключительного review также проверены.

- `freeze.json`: входные SHA и начальные состояния;

Для нового повтора создать новый отсутствующий каталог, скопировать туда только
`freeze.json` этого задания. Драйвер проверит хеши входов, policy и состав всех 11 пар;
для каждого режима создаёт новый подкаталог и отказывается перезаписывать старый.

```bash
python3 -B experiments/ors-routing-poc/revision_review.py \
  --source "$PWD" --evidence "$PWD/data/reports/ors-routing-poc-2026-10-26" \
  --output "$PWD/data/reports/ors-checker-new-replay" --mode walking
python3 -B experiments/ors-routing-poc/revision_review.py \
  --source "$PWD" --evidence "$PWD/data/reports/ors-routing-poc-2026-10-26" \
  --output "$PWD/data/reports/ors-checker-new-replay" --mode driving
python3 -B -m unittest discover -s experiments/ors-routing-poc -p 'test*.py' -v
```

Существующие tracked-файлы и staged-содержимое сохранены относительно начала
этого задания, включая прежнее изменение docs/README.md. Из файлов прежнего
эксперимента изменены только README/PROVENANCE — добавлены ссылки и описание v2.
Исходный REPORT, v1-модули, policy, raw-ответы, графы и их ведомости сохранены.
Производственный код, БД, `.env`, Compose, volumes, assets и OSRM не менялись;
Docker и сеть в этой ревизии не использовались. Коммиты/push не выполнялись.

## Решение о следующем шаге

Первоначальное предположение «для ORS нужно добиться буквальной геометрии OSRM
или собирать свой движок» больше не является основанием для остановки: часть
линий доказуемо сопоставляется через исходные ways без fork. Ревизия завершена;
бесконечно дорабатывать checker вместо продукта не предлагается.

Перед продуктовым подключением нужен отдельный ограниченный этап: проверить
пеший пользовательский сценарий с явным уточнением дорожной точки на небольшой
заранее выбранной выборке публичных мест. Оценивать следует успешный понятный
путь уточнения и честные отказы, сохраняя текущие регрессии. Это предложение,
не начатая интеграция. Автомобильный OSRM сохраняется; миграция car, собственный
fork и изохроны не утверждены этим результатом.
