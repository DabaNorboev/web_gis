# ORS: результат локального эксперимента 26.10.2026

**Статус: эксперимент выполнен; переключение приложения на ORS не выполнялось.**
ORS действительно построил пешие и автомобильные маршруты на сохранённых данных
Красноярска. Это подтверждение работоспособности движка, а не готовый безопасный
provider или подтверждение реального прохода/въезда.

## Ответы движка и оценка пригодности

Из 11 пар одна заведомо вне пилота; она отклонена до HTTP в обоих режимах.
Для оставшихся десяти пеший ORS вернул **9 линий**, автомобильный — **10**.
В пешем Солнечном ORS не нашёл второй конец в пределах 20 м; порог не повышался.
Среди десяти есть отрицательные контроли, поэтому 9/10 и 10/10 **не являются**
долей безопасных маршрутов или городского покрытия.

Длины в таблице — **сырые значения модели движка**. Модельное время сохранено
только для диагностики; оно не проверялось по реальным поездкам и не оценивает
пробки, парковку, подход или вход. В offline review пользовательские расстояние
и время остаются `null`.

Текущий строгий checker подтвердил согласованность только пешего hotel; по пяти
обычным пешим парам нет полного прохождения. Для автомобиля ни одна обычная пара
не прошла полное сопоставление исходных сегментов. Эти числа нельзя напрямую
сравнивать с прежними OSRM 1/5 пешком или 4/5 автомобилем: сегодняшняя проверка
ORS блокируется также несовместимостью представления геометрии, а новые native
OSRM-запросы и одинаковый сравнительный benchmark сейчас не выполнялись.

## Почему полной геометрии API недостаточно

При `geometry_simplify:false` ORS всё равно пропускает исходные промежуточные
вершины. Проверены конкретные случаи:

- Пеший правый берег: исходная вершина `way/194057373` отстоит от возвращённой
  хорды на ~0,67 м, у `way/612569213` — ~0,83 м.
- Автомобильный центр: ~0,44 м у `way/28790004`, ~0,60 м у `way/245591991`.
- Есть также практически коллинеарные пропуски. Текущий исторический matcher
  требует один исходный сегмент и не умеет доказывать цепочку таких сегментов.

Разбор **закреплённых** исходников ORS v10.1.0 и его GraphHopper v4.16.0:
`OSMReaderConfig` задаёт импортное упрощение 1 м; GraphHopper умеет отключить
его своим `routing.way_point_max_distance=0`. Но `BuildProperties` и
`ORSGraphHopperConfig.createGHSettings` ORS не передают этот произвольный параметр
из YAML. У API-запроса нет возможности восстановить уже удалённые вершины.
Подтверждённой штатной настройки ORS для отключения этого этапа не найдено.
Собственный образ или модификация ORS в этом задании не создавались.

`OsmId` полезен для происхождения, но сообщает IDs **ways**, тогда как текущая
защита автомобильного provider основана на исходных **node annotations**,
соседстве и направлении. Подставлять одно вместо другого нельзя. Адаптация
потребует отдельного доказательства исходной цепочки и переходов; допуск 0,25 м
в данном эксперименте не ослаблялся. Неудача этого matcher не доказывает плохое
качество ORS: это конкретная незакрытая задача совместимости и проверки.

Экспериментальный checker также не доказывает все переходы между совпавшими
геометрически сегментами по общим исходным node IDs и не валидирует всю систему
автомобильных turn restrictions. Поэтому даже его положительный статус нельзя
приравнивать к полному контракту текущего provider.

## Матрицы, изохроны и ресурсы

- Все девять отдельных pair-directions из контрольной матрицы 3×3 дали HTTP 200
  в обоих режимах. Их геометрия сохранена, но не проходила полный отдельный
  source-review; это не девять принятых поездок.
- Native matrix пешком: HTTP 500 / code 6020, превышен штатный лимит посещённых
  узлов. Native matrix автомобилем: HTTP 200. Повышение лимитов/настройка CH
  не выполнялись. Матрица использовала стандартный поиск привязки ORS и не
  является доказательством соблюдения пределов 20/35 м; pair-directions эти
  пределы задают явно. Matrix нельзя выдавать вместо проверенных линий.
- Изохрона 600 секунд от публичной контрольной точки: оба профиля вернули
  HTTP 200 и один GeoJSON-полигон. Это проверка доступности механизма;
  отверстия/барьеры/достижимость зданий внутри полигона не валидированы.

| Измерение | Пеший | Автомобильный |
|---|---:|---:|
| От запуска нового контейнера до готовности, включая подготовку графа | 20,96 с | 20,94 с |
| Пик cgroup memory за подготовку и запросы | 862,09 MiB | 825,72 MiB |
| Граф на диске | 24,03 MiB | 29,04 MiB |
| Warm route p95, 20 запросов после 3 прогревов | 5,96 мс | 3,93 мс |

По одному контейнеру одновременно; лимит 2 CPU / 3 GiB, swap не разрешён,
Java heap до 2 GiB. Пик измерен через `memory.peak`, а не выведен из лимита.
Warm-цифры включают локальный HTTP helper, относятся к одной контрольной паре
на данном компьютере, не являются нагрузочным SLA. Cold HTTP отдельно не
измерялся; время запуска выше нельзя называть временем одного cold route.
Общее время подготовки/прогона и CPU счётчики сохранены в runtime.json.

- `checks.json`, `preservation.json`, `evidence-sha256.json` — завершающие проверки

Исправленный драйвер дополнительно проверен настоящим повтором обоих профилей
в новом каталоге `data/reports/ors-routing-poc-2026-10-26-replay`: **для всех 11
контролей в каждом режиме совпали HTTP-статусы, геометрия, свойства маршрутов
и причины отказов**. Готовность — 21,00/21,09 с; очистка и сбор диагностики без

детерминированные значения. Результат — `replay-comparison.json`; повтор не
перезаписал первый прогон.

Пройдены **18 целевых синтетических тестов**: ORS adapter, access/direction, malformed
геометрию, полноту OsmId, сохранение null и отказ от принятия неизвестного.
Проверки очистки драйвера дополнительно используют имитацию отказов, не Docker
или рабочую БД. Точные количества/команда — в checks.json; это новые результаты,
а не тесты приложения из старых отчётов. Laravel/frontend/GIS suites не запускались:
производственный код и текущий контракт не менялись.

Исходные tracked-файлы сохранены, кроме добавленной ссылки в docs/README.md;
новый код находится только в experiments/ors-routing-poc. HEAD и staged-содержимое сохранены.
Рабочая БД, `.env`, volumes, текущий OSRM runtime, Compose и assets не читались
для изменения и не переписывались. Новые контейнеры ORS/helpers удалены после
прогонов; скачанный закреплённый образ и исследовательские графы оставлены.
Коммиты и push этого эксперимента не выполнялись.

## Решение о продолжении

**ORS остаётся разумным кандидатом для пешего режима и будущих изохрон.**
Запуск и ресурсы на этой выборке не стали препятствием. Но ORS не устранил
автоматически старые проблемы входов, стены и неопределённых пересечений.

Текущий этап закончен. До продуктовой интеграции нужен отдельный ограниченный
шаг: определить совместимый способ доказательства исходной цепочки ORS и её
переходов, сохранив guards; затем повторить ту же выборку. Если это требует
поддержки собственного fork движка или несоразмерного объёма работ, оценить
альтернативу до миграции. Замена работающего автомобильного OSRM и превращение
изохрон в обязательную функцию этим экспериментом не утверждаются.
