# Диагностика автомобильного пилота: контракт v1

Добавлена в Goal 5 (23.10.2026) для будущего интерфейса Goal 6. Страница `/trips`
пока использует прежние сообщения. Входной JSON, fragment version1, статусы,
`reason`, `checks`, `road_choices`, `snaps`, метрики и null при отказе сохранены.
Новые поля необязательны для старых клиентов/фикстур. TypeScript: `types/trips.ts`.

## Результат одной поездки

`results[i].diagnostics = {version: 1, issues: [...]}`. При успехе `issues: []`.
Каждая причина имеет поля:

| Поле | Значения и смысл |
|---|---|
| `code` | Машинный код проверки; не разбирать текст `reason` |
| `category` | `distance`, `ambiguity`, `obstacle`, `access`, `coverage`, `service`, `check_failure`, `insufficient_data` |
| `stage` | `scope`, `snap`, `connector`, `routing`, `geometry`, `route` (общий резервный этап) |
| `location` | `start`, `target`, `both_endpoints`, `route`, `unknown` |
| `target_index` | Нулевой индекс цели **в этом запросе**, только для `target` / `both_endpoints`; иначе `null` |

Индекс не является постоянным ID места. При запросе одной цели он равен 0,
даже если клиент показывает её третьей карточкой. Клиент использует тот же
контекст запроса, которым сопоставляет существующий `results[].index`.

Одинаковая причина одного этапа у обоих концов объединяется в `both_endpoints`.
Разные причины у концов остаются отдельными. Несколько причин могут действовать
одновременно; категории и проценты не следует складывать. Старый общий
`SNAP_NO_SAFE_CANDIDATE` остаётся в `checks`, но не дублирует более точную причину
в `diagnostics.issues`. Коды диагностик могут быть точнее старых `checks`.

Пример: вторая цель запроса не привязывается в радиусе; старт проверен:

```json
{
  "version": 1,
  "issues": [{
    "code": "SNAP_RADIUS_EXCEEDED",
    "category": "distance",
    "stage": "snap",
    "location": "target",
    "target_index": 1
  }]
}
```

`location: route` означает конфликт на автомобильной линии, а не ошибку исходной
точки. Конфликт первого/последнего совпавшего исходного ребра может иметь
`start`/`target`, если положение непосредственно установлено проверкой. Проверки
внутренних source nodes/edges передают `route`: их близость к концу не используется
для догадки. `unknown` обязателен, если положение не установлено: в частности,
парный OSRM `NoSegment` не сообщает, какой конец не сопоставлен с графом.
Сетевой отказ также не означает ошибку старта или цели.

## Основные семейства кодов

| Коды | Категория / ограничения интерпретации |
|---|---|
| `SNAP_RADIUS_EXCEEDED`, `SNAP_HINT_OUTSIDE_RADIUS`, `SNAP_LIMIT_EXCEEDED` | `distance`; не расширять радиус на клиенте |
| `SNAP_CHOICE_REQUIRED` | `ambiguity`; нужен явный дорожный выбор |
| `SNAP_THROUGH_*`, `SNAP_CROSSES_ROAD`, `ROUTE_BARRIER_REVIEW`, конфликты зданий/воды/железной дороги | `obstacle`; наличие конфликта модели, не доказанная непроходимость сегодня |
| `*ACCESS*`, `SOURCE_DIRECTION_OR_CONDITION_UNKNOWN` | `access`; нет достаточного разрешения для принятия, не объявлять всегда юридическим запретом |
| `SNAP_ROAD_DATA_MISSING`, `SNAP_SEARCH_INCOMPLETE`, `SNAP_DATA_UNAVAILABLE`, `ROUTE_DATA_UNAVAILABLE`, `ROUTING_DATA_UNAVAILABLE`, `INCOMPLETE_SOURCE_MATCH`, `SOURCE_ANNOTATIONS_INSUFFICIENT`, `ROUTER_NO_SEGMENT` | `insufficient_data`; отсутствие подготовленных/проверяемых сведений не превращается в отсутствие дороги |
| `SNAP_CANDIDATE_BUDGET` | `insufficient_data`; поиск ограничен бюджетом, уникальность не доказана |
| `OUTSIDE_CONFIRMED_COVERAGE` | `coverage`; исходный конец или автомобильная линия согласно `location` |
| `ROUTER_UNAVAILABLE` | `service`, положение `unknown`; повтор без обязательной перестановки точек |
| `SNAP_CHECK_FAILED`, `ROUTE_CHECK_FAILED` | `check_failure`; проверка не завершилась, это само по себе не доказательство конкретного дефекта реализации |
| `ROUTER_ENDPOINT_MISMATCH`, `NO_ROUTE`, `ROUTE_NOT_CONFIRMED` | `insufficient_data`; неверный фактический конец, отсутствие пути в графе либо общий резервный результат |

При неизвестном будущем коде клиент показывает общее сообщение, сохраняет
`unknown`, если иной локализации нет, и не выбирает ближайший конец по координатам.
Точные rejected OSM IDs, геометрии препятствий, SQL и исключения не передаются.

## Диагностика каждого конца

После успешно выполненного поиска:

```json
{
  "radius_m": 35,
  "nearest_road_distance_m": 43.64,
  "nearest_road_scope": "loaded_guard_cells",
  "containing_building_count": 1,
  "entrance_data": "NOT_PREPARED",
  "candidate_count": 0,
  "safe_candidate_count": 0
}
```

Находится в `road_choices.start.diagnostics` и `road_choices.target.diagnostics`.
При сбое загрузки/проверки либо раннем отказе поля может не быть: не подставлять нули.
`nearest_road_distance_m` — минимум до геометрии автомобильного класса среди
**загруженных guard-ячеек**, независимо от разрешения доступа. Не глобально
ближайшая доступная дорога, не результат привязки OSRM. При отсутствии дорожных
геометрий — `null`. Ноль допустим при реальном совпадении.

Расстояния кандидатов/диагностики — EPSG:32646, метры. `candidate_count` и
`safe_candidate_count` считают сырые положения на исходных сегментах до
объединения общей вершины/полосы неоднозначности/бюджета. Они не равны числу
вариантов UI. Список для выбора — только прежний `candidates`.

`containing_building_count` — число исходных контуров, покрывающих координату
по геометрии, не утверждение о выбранном пользователем здании. Из-за численного
округления точка ровно на границе может иметь 0; это поле не управляет допуском.
`entrance_data: NOT_PREPARED` означает отсутствие подготовленного источника входов;
нельзя отображать «входов нет» или выводить доступ из контура.

Ручной hint и автоматический выбор проходят те же проверки. Пунктир между
исходной и дорожной точкой по-прежнему не является маршрутом и не входит в
метры/секунды. Даже успешная проверка модели не подтверждает вход или парковку.
