# Г1: DaData, Geoapify и LocationIQ для Красноярска

**Статус: реальная проверка Geoapify/LocationIQ; DaData исключена из автоматического прогона по условиям сервиса.**
Публичные официальные страницы проверены 15.11.2026. Собственные ключи владельца
подключены непосредственно к процессам из выделенного файла `KEY=VALUE`;
значения, заголовки авторизации и URL с ключами не выводились. `.env` не читался
и не изменялся. Отдельное разрешение DaData не предоставлено; её отсутствие
в измерениях не оценивается как плохое качество. Настоящая ручная проверка
и запрос разъяснения оставлены за рамками по указанию владельца.

Границы — [контракт поиска](../features/address-search.md#переход-на-внешние-геокодеры),
[Г1–Г5](../plans/roadmap.md#переход-адресного-поиска-г1г5).
Приложение, API, UI, БД, Compose, рабочие данные и сборка не менялись.

## Закреплённая выборка и ориентиры

Единственный машиночитаемый набор — [corpus.json](../../scripts/geocoder-benchmark/corpus.json):
48 уникальных публичных адресных строк, по 8 в группах `ordinary`, `suffix`, `private`,
`snt`, `newbuild`, `ambiguous_edge`. Источники, локаторы, ожидаемый адрес/уровень,
уверенность, ограничения и `coordinate: null` записаны до первого API-вызова.
Варианты — 12 дополнительных строк тех же примеров: по два в группе,
шесть опечаток «Краснояркс» и шесть сокращений. Они не увеличивают число адресов
и не образуют отдельную независимую выборку. Префикс — строка без последнего
символа номера/суффикса, когда он длиннее одного символа; иначе полный ввод.
Это одна пауза во вводе, не все нажатия клавиш и не измерение UX.

| Группа / ID | Независимый ориентир | Уверенность / предел |
|---|---|---|
| Обычные дома A01–A08 | Муниципальный список домов, `municipal-housing` | Средняя для текста; исторический список не подтверждает текущую геометрию |
| Суффиксы A09–A16 | Муниципальный список, контакты СФУ, одна публичная ВКР | Средняя; A16 низкая: строение известно только по старому исследованию |
| Частный сектор A17–A24 | Муниципальный реестр участков ИЖС | Средняя для участка; существование/адрес дома не подтверждены |
| СНТ A25–A32 | Муниципальные реестры садовых участков и ИЖС | Низкая для современного написания/привязки; участок не дом |
| Новостройки A33–A40 | Семь карточек СИБДОМ с почтовым адресом/вводом 2024–2025; публикация застройщика о Взлётной, 46 | Средняя; вторичные карточки требуют первичных документов, A40 — адрес выдачи ключей |
| Неоднозначные / окраины A41–A48 | Муниципальный список: Базайская, Новая, Норильская и другие | Средняя для написания, расположение пока не проверено |

Все ссылки и точные ориентиры находятся в `sources`/`reference` набора;
совпадение трёх API не используется как подтверждение. Муниципальные таблицы
не содержат личных имён в выборке; квартиры/собственники/личные места не включены.
Выборка стратифицированная, не случайная: значительная доля исторических
муниципальных адресов, СНТ нескольких обществ и только восемь новых домов.
Она не оценивает долю правильных адресов по всему Красноярску.

**Пригодных независимых координатных эталонов сейчас 0/48.** Текстовый адрес
не является центроидом здания, участком или входом. Ошибка в метрах не считается;
во всех строках `null` с причиной. Для продолжения координатной части нужны
отдельно полученные, датированные и разрешённые к использованию контуры/точки
с подтверждённой адресной идентичностью. OSM не считать полностью независимым
эталоном для сервисов, которые могут использовать OSM. Метод будущего измерения:
минимальное расстояние до подтверждённого контура в EPSG:32646, либо до независимо
измеренной точки с явно указанной её ролью и погрешностью; не расстояние между API.
Этот runner намеренно пока не содержит вычисления метрик без таких входов.

Четыре фиксированных публичных контрольных точки R01–R04 охватывают центр,
Татышев, Академгородок и Солнечный. Это приблизительные точки для проверки
уровня/пустого reverse и неизменности исходной координаты, не адресные эталоны.
Даже правдоподобный ближайший дом не подтверждает принадлежность точки зданию.

## Фактические результаты

Результат получен из shell на этой машине, с разрешённым сетевым запуском;
доступность из PHP-контейнера/целевого сервера не проверялась. Сравнение MapLibre
по документации, карта не подключалась. DaData: **автоматический прогон не выполнен
из-за условий сервиса**; в сравнительные знаменатели она не включена.

Это **строгие текстовые совпадения, не точность геокодирования**: 26/31 не оценивает координаты. Координатных эталонов нет; частный сектор и СНТ остаются существенным ограничением проверки. Совпадение требует текста
независимого ориентира и строгой нормализации, а не согласия сервисов. Алиасы,
историчность адресов и отсутствие геометрии ограничивают вывод; ниже приведены
случаи, в которых отсутствие строгого совпадения нельзя считать ошибкой API.

Основной проход: по 48 полных поисков и 48 autocomplete, по 12 вариантов и
4 reverse у каждого. У Geoapify один полный поиск закончился транспортной ошибкой;
у LocationIQ одна подсказка — транспортной ошибкой, шесть — 404 (СНТ A27–A32).
У Geoapify шесть autocomplete вернули HTTP 200 с пустой выдачей.
Отдельный полный текстовый проход: 48 поисков на сервис; у LocationIQ A31
закончился транспортной ошибкой (СНТ вне домового знаменателя).
В 8/8 reverse-вызовах получены HTTP 200 и по одному результату, но правильность
ближайшего дома для контрольных точек не установлена.

Всего **321 попытка**: 224 операции основного протокола + 96 отдельного текстового
прохода + 1 повтор первого Geoapify search после смены сетевого режима.
Первая попытка оборвалась за 3,74 мс без HTTP; серверное получение неизвестно,
поэтому она всё равно засчитана. Другие неудачные операции не повторялись.
Три дальнейших транспортных события длились около 15 с; в последнем запуске
безопасно записан класс `URLError`, полный текст ошибки не сохранён.
Итог: 311 HTTP 200, шесть 404, четыре события без HTTP. Точный списанный баланс
ключей не запрашивался; консервативный расход бюджета — все 321 попытка.
Официальные Free-лимиты не заменяют неизвестный текущий тариф владельца.

Интервал с первой попытки до последнего ответа: **15 мин 08,37 с**, из них
**617,84 с активных HTTP-попыток** (Geoapify 418,32 с; LocationIQ 199,52 с),
остальное — интервалы, остановки и независимая работа. Время UTC
08:56:44–09:11:52, местное 15:56:44–16:11:52 15.11.2026.
Нагрузочного теста не было. Это один запуск с последовательными соединениями,
без доказательства SLA/устойчивости или свежести источников.

### Наблюдения, влияющие на выбор

- **Суффикс нельзя терять.** В выдаче обоих встречается Автомобилистов, 70А
  вместо подтверждённого `70а, корпус 1` (A09). Это не подтверждение корпуса.
  Для Киренского (A14) присутствуют несколько университетских объектов и
  альтернативная запись `26Б, 26 к1`; без отдельного подтверждения она не сливается
  с исходным адресом. Ломоносова, 118а (A12) строгого совпадения не дал ни один.
- **Дробь не эквивалентна основному номеру.** Для Караульной, 39/4 (A33)
  строгого совпадения нет у обоих; среди response data есть дом 39 и иные
  номера/строения. Их координаты нельзя молча принять за 39/4.
- **Есть полезная разница полноты.** Geoapify вернул Норильскую, 64 (A37)
  и Взлётную, 46 (A40) как `building`; LocationIQ по этим примерам не дал строгого
  номера, в response data присутствует уровень улицы (`residential`/`secondary`).
  Статус нового дома A40 всё ещё ограничен источником об адресе выдачи ключей.
- **Есть алиасы, а не доказанные ошибки.** Вавилова / Академика Вавилова (A01)
  и Киренского / Академика Киренского (A14) требуют адресного alias-правила.
  Для Базайской у LocationIQ есть response data дома 357 с `Krasnojarsk` в подписи,
  тогда как строгий оценщик не принимает латинскую подпись при отсутствии city.
  Поэтому различие A41/A42 в автоматической метрике требует ручного разбора,
  а не заявления о неверном геокодировании. Типы `null`/`yes` в LocationIQ
  не становятся измеренной точностью дома только из-за наличия координат.
- **Город надо проверять отдельно.** В response data неточного ввода есть
  Вавилова, 94 в Борском Самарской области и Кутузова в Богучанах. У полных
  поисков ИЖС/СНТ встречаются другие населённые пункты. `countrycodes=ru`
  и мягкое предпочтение области не гарантируют Красноярск. Параметры scope
  у поставщиков различаются; полный текст во всех запросах содержит Красноярск,
  Geoapify использует country filter + proximity bias, LocationIQ — countrycodes
  + viewbox с `bounded=0`. Это сравнение практических настроек, не одинаковой
  серверной географической фильтрации.
- **Выбранные координаты действительно возвращаются.** Контрольный пример
  A10, Аэровокзальная 8Ж: response data Geoapify содержит `(92.9015248, 56.029352)`
  и `building`, LocationIQ — `(92.9015490, 56.0293420)` и `apartments` (`lon, lat`).
  Это окончательные поля выбранного снимка, отдельного HTTP details не нужно.
  Совпадение адреса и близкие точки не доказывают измеренную точность/вход;
  ошибку в метрах между этими точками вместо независимого эталона не считали.

Нативные provider ID/признаки происхождения сохранены только в разрешённых response
 data. Дата/версия исходного адресного снимка в метрики не выдумана: неизвестна;
время получения не является датой наблюдения здания.

## Воспроизведение и допустимые свидетельства

Python 3 стандартной библиотеки, Linux (`fcntl`); без зависимостей приложения.
Запуск из корня checkout. Offline-команды не используют сеть и не пишут кэш:

```bash
python3 -B scripts/geocoder-benchmark/benchmark.py --providers geoapify locationiq
python3 -B -m unittest discover -s scripts/geocoder-benchmark -p 'test_*.py' -v
```

Реальный запуск использует только собственные ключи и новый output. Файл ключей
не исполняется как shell: читаются только три разрешённых имени переменных.
Значения загружаются в окружение процесса; содержимое файла не журналируется.

```bash
python3 -B scripts/geocoder-benchmark/benchmark.py --run --collect \
  --providers geoapify locationiq \
  --keys-file /home/daba/.config/placelens/geocoders.keys \
  --out data/reports/geocoders/g1-new-run \
  --ledger data/reports/geocoders/g1-request-budget.jsonl
python3 -B scripts/geocoder-benchmark/summarize.py \
  data/reports/geocoders/g1-new-run/metrics.jsonl
```

Один общий ledger для всех запусков Г1; смена output не обнуляет бюджет.
До сети записывается резервирование с `fsync`, есть exclusive lock. Не удалять
и не менять ledger ради повторения. Полная двухпровайдерная процедура —
**112 + 112 = 224 запроса**: 96 полного поиска, 96 autocomplete, 24 варианта
и 8 reverse. Выбранные координаты уже содержатся в ответе; фиктивного details
запроса нет. `--search-only` запускает отдельный проход 48 полных адресов на
поставщика для единой строгой текстовой оценки; это ещё 96 запросов, а не
бесплатная обработка. Два прохода вместе — 320 без дополнительных попыток.

При транспортной остановке `--continue-unattempted` с тем же ledger и новым
output пропускает **все** прежние резервирования, включая неудачные, и отправляет
только другие операции. Квотные/авторизационные ошибки не обходить этим флагом.
Для повторного полного исследования в рамках текущего лимита может не хватить
остатка: runner обязан отказать. После окончания Г1 новое исследование требует
своего согласованного бюджета; приведённые команды не разрешают обнулить текущий.

Жёсткий API-предел — 400, ещё 200 зарезервированы на страницы условий/ориентиров;
это резерв, не число выполненных запросов документации. Внутренний HTTP fan-out
поискового инструмента не наблюдаем, поэтому точного общего числа его HTTP
соединений здесь нет. Все API-попытки, включая сетевые ошибки и повторы,
учтены отдельными строками ledger; итоговый расход приведён выше.

Запросы последовательные, интервал старта ≥1,2 с, до 1 MiB ответа, socket timeout
15 с, redirects и автоматические retries отключены. Это не общий deadline: у обоих сервисов наблюдались долгие autocomplete, некоторые попытки Geoapify превышали 20 с. Socket timeout не ограничивал всю операцию; жёсткий предел требует отдельного механизма и проверки. В ранних запусках любая
транспортная ошибка останавливала процесс; текущий runner пропускает такую
операцию без повтора и останавливается после трёх последовательных транспортных
ошибок. Авторизационные/квотные и прочие HTTP-ошибки кроме 404 останавливают запуск.
404 и успешная пустая выдача сохраняются раздельно. Искусственных отказов/нагрузки
на реальные сервисы нет. Тест 429 — исключительно синтетический.

Сохраняются hashes набора/runner/evaluator, время UTC, ID публичного примера,
метод, HTTP-код, число результатов и задержка. Отдельно — уникальные разрешённые
**response data** (подпись, координаты, ID в пространстве поставщика, исходные
признаки точности), без исходного запроса, HTTP-конверта, последовательности
запросов и связи с case ID. Для LocationIQ это разрешённое хранение response data,
а не кэш пар request-response. Полные HTTP-ответы и пары не архивируются; для
переиспользуемого серверного кэша по-прежнему действует ограничение Free 48 часов.
Тексты исключений и ключи не сохраняются. Ответы DaData не получались.

Из-за такой политики невозможно позднее восстановить порядок всех кандидатов
первого прохода из архива response data. При получении ответа отдельно сохраняется
производная оценка по заранее закреплённому независимому тексту: номер первого
строгого совпадения, заявленные уровни, наличие координат, другой город и причины
неизвестности. Ранние проходы ещё не имели единой версии оценщика; их текстовые
оценки нельзя смешивать с отдельным полным `--search-only` проходом.

Оценщик [evaluate.py](../../scripts/geocoder-benchmark/evaluate.py) приводит только
регистр, NFC, ё/е, пробелы и тип улицы, сопоставляет улицу, полный номер с суффиксами
и Красноярск (допустимы явные латинские записи города). В отсутствие поля city
принимается отдельный компонент «Красноярск» в подписи, не «Красноярский край».
Нет fuzzy matching, удаления «Академика», автоматического объединения альтернативных
номеров или корпуса с основным домом. **Нет строгого совпадения не означает
ошибочный адрес**: это может быть алиас, неполный ответ или недостаточный ориентир.
ИЖС/СНТ не получают оценку дома по номеру участка; низкая уверенность исключается
из знаменателя строгих метрик. Поддержанных текстовых ориентиров — 31/48;
пространственно подтверждённых — 0/48. Методические ограничения видны в таблицах.

Агрегатор —
[summarize.py](../../scripts/geocoder-benchmark/summarize.py). Он выводит запросы,
ошибки, p50/p95 по методам и строгие текстовые совпадения по группам. Метрики
без измерения остаются null. Задержки включают DNS/TLS/сеть, первый запрос не
исключается; серверная обработка и фронтенд debounce отдельно не измерялись.

## Предварительное решение и вопросы Г2

**Рекомендован основной кандидат Geoapify**, с ограничением: это выбор для
дальнейшего проектирования Г2 по текущей стратифицированной проверке, не гарантия
точности всего города. Основания: больше подтверждённых строгих совпадений,
дома A37/A40 вместо улицы, прозрачнее разрешение хранения/MapLibre.
Цена выбора — большая задержка и длинный хвост, поэтому нужны ограниченное
ожидание UI, защита от поздних ответов, повтор без накопления запросов и независимый
анализ явно выбранной точки. Жёсткий deadline нельзя обещать без отдельного механизма
полного ограничения длительности операции.

**LocationIQ как резерв сейчас не обоснован.** Среди 31 поддержанного текстового
ориентира его строгие совпадения — подмножество Geoapify: дополнительных 0.
Даже если отдельно принять латинские алиасы Базайской, эти дома уже найдены
Geoapify; доказанного нового покрытия они резерву не дают. У обоих остаются
суффиксные/дробные случаи, у обоих неизвестна геометрическая ошибка. Быстрота
LocationIQ сама по себе не доказывает необходимость резерва; улучшение доступности
при отказе основного этим последовательным запуском не измерено. Если продукту
понадобится отдельное SLA-основание, его нужно проверить и ограничить бюджетом.

**DaData не ранжируется.** Применимость к настоящему интерактивному поиску с явным
выбором сохраняется; ручную проверку/разъяснение можно рассмотреть отдельно для
непокрытых случаев. Ни платная «Стандартизация», ни имитация пользователя не запускались.
ИЖС/СНТ и координатная точность остаются существенной непроверенной частью Г1;
по ним нельзя объявить поставщика победителем или подтвердить резерв.

Минимальная нормализация: NFC, пробелы, регистр/ё–е для сопоставления, исходная
строка отдельно; корпус/строение/литера/дробь сохраняются (A09/A33).
Алиасы «Академика» и латинского города — отдельные проверяемые правила Г2,
не глобальное удаление слов или замена алфавита. После ответа проверять город,
полный номер и уровень; не выбирать первый вариант только из-за непустых
координат, POI-названия или высокого `confidence`. Идентичность провайдеров не сливать.
Первая реализация проектируется с одним активным Geoapify и возможностью замены
provider, без подключения LocationIQ как рабочего резерва. Обычный ввод — без fan-out
и автоматического резервного поиска по пустоте. Ни одного этих правил в приложение здесь не внедрено.

Предлагаемый старт кэша для Г2, **не действующий контракт**: Geoapify autocomplete
5 минут, окончательные данные 24 часа, reverse по точной исходной координате
1 час; подтверждённая пустая выдача до 60 секунд, ошибки/квота не превращаются
в отрицательный адресный кэш. Это инженерные начальные TTL, не измеренные
оптимумы и не сроки обновления поставщика: короткие подсказки уменьшают повторные
обращения при наблюдавшемся длинном хвосте, окончательные сведения отделены от
вариативного ввода. Сохранение места/URL сверх TTL решается отдельно. Лимит числа
записей выбрать по реальному бюджету приложения в Г2; benchmark его не измерял.
Ключ: provider + method + существенные параметры scope/языка + версия нормализации;
reverse не округляет и не сдвигает точку. Если когда-либо понадобится LocationIQ,
для request-response кэша Free не превышать 48 часов. Кэш DaData до выяснения
прав не проектировать как бессрочный. Сам факт разрешения хранения Geoapify
не означает бессрочно хранить пользовательский ввод или личные координаты.

Общий benchmark повторно не нужен. Для конкретных решений Г2 сначала использовать
сохранённые ответы; новые сетевые проверки требуют отдельного обоснования.
Основное место целевых требований — [контракт поиска](../features/address-search.md#переход-на-внешние-геокодеры).

Конкретные вопросы Г2 (без начала реализации в этом задании):

1. Как ограничить целевую территорию без подмены proximity bias, сохранить полный
   номер и нормализовать точность при одном активном Geoapify с возможностью замены?
   Какие пределы ожидания, механизм общего ограничения времени и правила повтора
   исключают накопление запросов и применение поздних ответов?
2. Можно ли принять участок СНТ/ИЖС без подтверждённого дома; какие уровни
   координат требуют уточнения точки; как показывать неизвестную точность?
3. Как представлены собственный ID, provider ID, `fias_id`/OSM-ID, выбранный снимок
   и окончательное подтверждение; как сохраняется совместимость прежних мест?
4. Разрешены ли выбранный способ использования DaData, MapLibre-атрибуция,
   хранение конечных координат/истории и архив исследования; какие права у Free
   Geoapify для production; как трактовать response data и request-response pairs
   LocationIQ в серверном кэше?
5. Каковы TTL/лимиты размера, отрицательный кэш, ключ reverse без сдвига точки,
   поведение выбранного места при истечении TTL и исчерпании общей квоты?
6. Какие текст/координаты уходят за пределы приложения, что показывать пользователю,
   какие поля допустимы в диагностике; нужны ли иные условия обработки данных?
