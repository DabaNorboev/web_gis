# Территория сервиса и покрытие данных

Граница сервиса и область загрузки данных разделены. Сервисная граница — сохранённый GeoJSON городского округа, OSM relation 1157393; это согласованный охват анализа, не основание заполнять неизвестный населённый пункт адреса. Внешний буфер расширяет только отбор данных: точка в буфере за сервисной границей остаётся вне покрытия сервиса.

## Хранение и расчёт

`dataset_coverages` содержит одну запись на `dataset_import_id`: исходную сервисную геометрию `service_geom`, геометрию отбора `data_geom`, `buffer_m` и SHA-256 границ. Геометрии — валидные непустые 2D Polygon/MultiPolygon, EPSG:4326; область отбора покрывает территорию сервиса. Запись публикуется в одной транзакции с объектами и переключением активного снимка. При ошибке прежние объекты и покрытие остаются активными. У старого снимка без этих метаданных покрытие неизвестно; оно не выводится из положения импортированных объектов.

Буфер строится офлайн: `ST_Transform(ST_Buffer(ST_Transform(service_geom,32646), buffer_m, 'quad_segs=16'),4326)`. EPSG:32646 — метрическая UTM 46N для Красноярска. В текущих рабочих наборах `buffer_m=1000`, максимальный пользовательский радиус — 500 м. Запас нужен в том числе из-за аппроксимации буфера и различия проекционных/геодезических расстояний. CLI допускает 0–5000 м; сам параметр буфера не служит доказательством покрытия конкретного радиуса.

Во время анализа `ST_Covers(service_geom, point)` определяет принадлежность территории (внешняя граница включена, внутренности отверстий исключены). Для точки внутри области данных `ST_Distance(point::geography, ST_Boundary(data_geom)::geography)` даёт `available_radius_m`. Радиус считается покрытым только при `available_radius_m >= radius_m`; в остальных случаях подсчёт неполон. Пустой список объектов не используется для определения покрытия.

Кандидат в ближайшие остановки определяется точным `ST_Distance` среди объектов зафиксированного снимка. Его расстояние может превышать выбранные 300/500 м, но не должно превышать `available_radius_m`: иначе неимпортированная точка за границей отбора могла бы оказаться ближе. В этом случае `nearest_stop=null`, значение расстояния `null`, доступность `INSUFFICIENT_DATA`. Проверка не доказывает полноту или актуальность самого исходного набора.

## Ответ транспортного API

`GET /api/v1/transport/analysis` возвращает `coverage`: `status`, `reason`, `dataset_import_id`, `radius_m`, `available_radius_m`, `buffer_m`, `service_boundary_sha256`, `data_boundary_sha256`.

| Статус покрытия | Поведение |
|---|---|
| `COVERED` | Географическая область отбора покрывает радиус. Пустой результат может быть нулём именно в импортированном наборе. Качество маршрутов/актуальность оцениваются независимо. |
| `PARTIAL` | Точка обслуживается, но область отбора обрезает радиус. Три счётчика (`stops_count`, `unique_routes_count`, `identified_routes_count`) — `null` / `INSUFFICIENT_DATA`. Найденные остановки можно показать как неполный список; ближайшая проверяется отдельно. |
| `OUTSIDE_SERVICE_AREA` | Все показатели — `null` / `UNAVAILABLE`, метод — `null`; остановки/ближайшая/маршруты не выдаются. UI показывает «Вне покрытия» и объяснение. Это HTTP 200 с предметным состоянием, не ошибка координат. |
| `UNKNOWN` | Источник или подтверждённая область отбора отсутствуют. Показатели — `null` / `UNAVAILABLE`; не возвращать фиктивный ноль. |

Существующая модель `quality` не меняется: пространственное покрытие не означает `freshness: CURRENT` и не заменяет известную дату наблюдения. `analysis_area` и `analysis_bounds` остаются геометрией выбранного радиуса, в том числе вне территории. Некорректные координаты/радиус по-прежнему дают HTTP 422. Смена точки, радиуса, сброс и возврат к адресу внутри города сохраняются.

## Офлайн-подготовка и повторение

Подготовка использует официальный CSV остановок и фиксированный Geofabrik PBF из [подготовки дорог](../data/osm-linear.md). Команды выполняются из корня проекта в целевом окружении:

```bash
docker compose exec php php artisan migrate
docker compose exec php php artisan gis:prepare-coverage \
  data/raw/boundaries/krasnoyarsk/2026-10-07/boundary.geojson \
  data/raw/boundaries/krasnoyarsk/2026-10-20-buffer-1000/selection.geojson --buffer-m=1000
```

Команда требует новый выходной файл. Он содержит точные байты геометрии для хеша подготовки; не добавлять форматирование или перевод строки. Сервисная граница SHA-256 `0a631518e68855b2eba44a72429b9a11fa95e0de075c013f523eafa4b84ef5f8`; отбор с буфером — `3e0bc35f2d8fef55aa864722b8018fd1e146b26f205a9fdbfbf7530a50dc67d9`.

Запустить существующие `scripts/prepare-osm-linear.py` и `scripts/prepare-osm-areas.py` по командам из [дорог](../data/osm-linear.md) / [площадных объектов](../data/osm-areas.md), заменив входную границу на `selection.geojson` и задав новые выходные каталоги. Для текущей подготовки использовались `--network=none`, 2 CPU, 1 ГиБ для линий и `--memory=1600m` для площадей. После успешного манифеста импортировать с **исходной сервисной границей** `--boundary=.../2026-10-07/boundary.geojson` и новым `--buffer-m=1000`. Не передавать буфер как сервисную границу: это расширит территорию обслуживания и создаст второй буфер.

Пример официальных остановок (CSV содержит сведения по краю, предварительной пространственной обрезки нет):

```bash
docker compose exec php php artisan transport:import-stops \
  data/raw/transport_stops/2025-05-31/stops.csv \
  --boundary=data/raw/boundaries/krasnoyarsk/2026-10-07/boundary.geojson \
  --buffer-m=1000 --source-version=20250531T1612 --source-updated-at=2025-05-31 --dry-run
```

Для OSM соответствующие команды `osm:import-linear roads|railways` / `osm:import-areas green_areas|water` принимают `--buffer-m`, `--expected-sha256` и `--report` как прежде. При буфере обязателен хеш точной области отбора в `preparation.boundary_sha256`: старый городской JSON нельзя объявить буферным. Если хеш подготовки указан без буфера, он также сверяется с границей. Для исходного JSON без метаданных подготовки при `--buffer-m=0` регистрируется лишь область отбора из предоставленного файла, полнота исходника не подтверждается. Геометрия и bbox манифеста не заменяют строгую проверку объектов в PostGIS. Некорректная граница или параметр буфера отклоняются до регистрации попытки. Публиковать только после проверки dry-run; повтор того же входа и конфигурации возвращает `skipped`, история сохраняется.
