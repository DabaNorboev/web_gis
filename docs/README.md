## Исследования и прошлые свидетельства

Эти каталоги не являются очередью исполнения и не включаются в контекст автоматически. Открывайте только выбранный материал по прямому указанию: [исследования](research/README.md), [история реализаций](history/README.md), [заменённые спецификации](archive/README.md). Полные исходные свидетельства сохранены. Датированные отчёты могут содержать действовавшие тогда команды и локальные пути; применимость устанавливается отдельно.

## Как вести документацию

1. Только AGENTS задаёт устойчивые правила работы. `product` — обещания реализованного продукта, `decisions` — принятые вводные, контракт функции — её поведение, roadmap — план. Не копировать состояние в несколько вводных файлов.
2. Новый текущий контракт размещать в features, runbook подготовки — в data, план/гипотезу — в plans, исследование — в research. Индексировать ссылкой в соответствующем README; checker проверяет достижимость из этого индекса.
3. Имена текущих контрактов, планов и исследований — без дат. Дата в имени допустима для отдельного исторического протокола в history; исходные архивные имена сохраняют происхождение.
4. Изменилось поведение или контракт — обновить основной документ, его updated и одну строку changelog со ссылкой на контракт. Правки оформления, переносы, рефакторинги и повторные прогоны в журнал не включать. Новый датированный отчёт создавать лишь для существенного самостоятельного опыта.
5. Каждый Markdown в docs имеет шапку: status, updated, verified; replaces добавляется при замене другого документа. updated — дата правки текста, verified — основание проверки, не обещание актуальности данных. При переносе без запуска сохраняется `not verified`; исторические результаты остаются в тексте с исходной датой.
6. Допустимые status: current — действующий контракт/runbook/индекс; plan — будущий объём; hypothesis — предположение; history — свидетельство прошлого; superseded — заменённая спецификация/рекомендация. Статус принятия конкретного этапа уточняется внутри плана, не выдумывается из шапки.
7. verified принимает `code`, `run YYYY-MM-DD` или `not verified`. Не отмечать весь документ проверенным запуском только из-за проверки ссылок. В шапках этой реорганизации нет новых утверждений о runtime.
8. Поле replaces содержит прежнее имя; в тексте дать относительную ссылку на сохранённый оригинал, если он существует. Обновить входящие ссылки при переносе. Политика размеров и уровни сообщений checker — в [testing](testing.md#проверка-документации); размер не является причиной удаления свидетельств.
9. Запуск checker — в testing. Относительные ссылки и якоря проверяются без сети; внешние URL и содержимое ignored-отчётов он не подтверждает. Нет необходимости перечитывать исследования ради каждой задачи.

```yaml
---
status: current
updated: 2026-10-27
verified: not verified
replaces: прежнее-имя.md
---
```

[План второго интерфейса](plans/interface-v2-plan.md) имеет статус plan: незавершённые этапы сохранены в исходном тексте. Его формализация и перенос не являются приёмкой интерфейса. Событие снятия обхода checker — [D08](decisions.md#d08-снятие-исключения-плана-интерфейса).

## Шаблон следующего задания

Для задачи, которой нужен план в репозитории, достаточно одного Markdown-файла с явным статусом и ссылкой из этой карты или индекса. Не создавать заранее дублирующие GOALS/PLANS/PROMPTS для каждой мысли.

```markdown
# Название
Статус: предложение / согласовано / в работе / завершено / отложено.

## Результат и пользовательский вопрос
## Границы файлов и что не входит
## Зависимости и источники
## Шаги и критерии завершения
## Проверки и их побочные эффекты
## Открытые вопросы и риски
```

Завершённый план сохраняет статус и ссылку на результат; не становится второй текущей спецификацией. Исправления и проверки текущего задания входят в его объём; переход к новому продуктовому этапу требует соответствующего задания пользователя.
