# Локальное окружение PlaceLens

Запуск приложения, OSRM и ORS в локальном окружении. Подготовку, импорт и миграции выполнять для явно выбранного окружения; существующие `.env`, ключи и volumes сохранять.

Команды ниже меняют окружение только при соответствующем поручении. Автомобильный режим обслуживает локальный OSRM, пеший — отдельный локальный ORS. API и ограничения — [поездки](features/trips.md).

## Стек и сервисы

PHP 8.4 / Laravel 13, PostgreSQL 16 / PostGIS 3.4, Vue 3 / TypeScript 6, Vite, MapLibre, Tailwind CSS 4 и shadcn-vue. Python ETL — одноразовая офлайн-подготовка, без постоянного сервиса. Точные зависимости — manifests/lock, версии контейнеров — Compose/Dockerfile; установленный пакет не означает реализованную функцию.

Базовые четыре сервиса: nginx, php, node, db. Nginx 80, Vite 5173 и БД 54325 опубликованы только на loopback. PHP использует `db:5432`; для IDE — `127.0.0.1:54325`, учётные данные из локального `.env`. Node-зависимости контейнера хранятся в named volume. Единственный Compose — `docker-compose.yml`; Node работает от пользователя node, Nginx ждёт готовности FPM и выбранных assets; Compose перезапускает Nginx после обновления PHP, чтобы применить новый адрес контейнера. Спутниковые данные подключаются отдельно и явно; чистый checkout не требует их наличия.

## PHP runtime с c-ares

`docker/php/Dockerfile.cares` — отдельный кандидат для внешнего геокодирования; штатный `Dockerfile` и Compose пока используют прежний runtime. Основа — официальный PHP 8.4.27 FPM / Alpine 3.24.4, закреплённый digest; пакетный libcurl 8.23.0 / c-ares 1.34.9, без собственной сборки curl. Composer также закреплён digest. Переход glibc → musl требует [проверок runtime](testing.md#внешний-поиск-г3); набор расширений сохраняется, полные ICU-данные установлены явно. DNS/transfer-бюджеты и runtime guard приложения не меняются.

Подготовка без замены используемого образа и контейнеров:

```bash
docker build -f docker/php/Dockerfile.cares \
  --build-arg UID="$(id -u)" --build-arg GID="$(id -g)" \
  -t placelens-php:cares-g3-20261115-verified docker/php
python3 -B tests/environment/check_geocoding_runtime.py --image placelens-php:cares-g3-20261115-verified
```

Приёмка 2026-11-15: отдельная сборка с использованием Docker cache дала `sha256:cb05e153e4987a356a4a5f90b279ade9580671dbad440251093cf4735351005d` (`linux/amd64`). PHP `curl_version()` подтвердил libcurl 8.23.0 / c-ares 1.34.9 / OpenSSL 3.5.9; PHP 8.4.27. CLI/backend/state/FPM прошли; результаты и границы — [testing](testing.md#внешний-поиск-г3). Локальная активация выполнена через явный override: [Г5](#локальное-геокодирование-г5); основной Compose сохраняет прежний default runtime.

Повторную сборку делать с новым тегом, сохраняя принятый image ID. APK-репозитории обновляются: digest фиксирует основу, но не все будущие пакеты `apk add`; manifest стенда фиксирует фактический состав. Для использования ровно проверенного runtime сохранять готовый образ по его ID (`docker image save` при переносе), а новую сборку принимать заново. Не заменять версии PHP/curl/c-ares или digest без проверки PHP `curl_version()` и стенда.

**Последующая рабочая активация — отдельное действие.** После разрешения и успешного стенда адресно добавить в `services.php` единственного `docker-compose.yml`:

```yaml
image: placelens-php:cares-g3-20261115-verified
build:
    context: ./docker/php
    dockerfile: Dockerfile.cares
    # Существующие args UID/GID сохранить.
```

Убедиться, что tag указывает на принятый image ID, сохранить локальную конфигурацию/сведения о текущем образе по правилам существующей активации ниже, затем:

```bash
docker compose config --quiet
docker compose up -d --no-deps --no-build --wait --wait-timeout 90 php nginx
docker compose exec php php -r 'echo PHP_VERSION,"\n"; $v=curl_version(); echo $v["version"]," / c-ares ",$v["ares"],"\n"; exit(empty($v["ares"]) || !($v["features"] & CURL_VERSION_ASYNCHDNS));'
```

`--no-build` активирует именно принятый образ; Compose сохраняет текущие environment/mounts/command/healthcheck, Nginx пересоздаётся при замене PHP, чтобы обновить адрес FPM. Перед этим отдельно проверить и согласовать текущее содержимое `docker/nginx/nginx.conf`: пересоздание прочитает в том числе подготовленные правки Г3. Проверить `/up` и независимый анализ точки в текущем окружении. Переключение runtime не настраивает ключ/`GEOCODING_ENABLED`, не применяет миграции и не разрешает реальный Geoapify; эти шаги остаются отдельной активацией внешнего поиска.

## Локальные спутники: рабочая активация

На ноутбуке подключены две даты TCI/NDVI: **06.06 и 09.09.2026**. Runtime и PNG монтируются read-only из `data/satellite/local-two-dates-2026-01/`. Игнорируемый `docker-compose.override.yml` задаёт оба mount, зафиксированные pins и настройки поиска для этого ноутбука. Режим assets — `build`. [Подготовка и форматы](data/satellite.md), [контракт спутникового блока](features/place-analysis.md#6-блок-satellite).

Из корня проекта:

```bash
docker compose up -d
```

Compose автоматически читает локальный override и использует новые пути и pins вместо прежних значений из сохранённого `.env`. В override нет ключа. Для PHP указан приватный файл `data/local/geocoding-g5/default-compose.env` с правами `0600`, содержащий только ключ Geoapify. При ротации ключа обновить его из разрешённого источника и повторить запуск. Прежняя обёртка и исходный helper сохранены для явного запуска. Согласованно удалены исходные каталоги четырёх дат 2024–2025 и прежние runtime и тайлы v2/v3. Готовые городские выпуски и свидетельства сохранены. Прежние каталоги runtime и тайлов можно заново собрать из готовых выпусков. Для повторной исходной подготовки четырёх дат понадобятся входные данные. Активация проверена через локальные Nginx/FPM. Подробности в ignored `data/satellite/local-two-dates-2026-01/activation-verification.json`.

Единый `docker-compose.yml` работает без спутниковых данных. При незаданных четырёх переменных ниже приложение получает пустые параметры источника и отвечает `UNAVAILABLE / SATELLITE_NOT_CONFIGURED`; остальные локальные результаты независимы. Вместо отсутствующих данных монтируется пустой tracked `docker/satellite-disabled`, только для чтения. Подготовка данных не входит в запуск приложения.

Для обычной активации в другом экземпляре с новым локальным `.env` задать пути и pins уже проверенного выпуска:

```dotenv
SATELLITE_RUNTIME_DIR=/absolute/path/to/prepared/runtime
SATELLITE_RUNTIME_SHA256=<trusted-runtime-catalog-sha256>
SATELLITE_DELIVERY_DIR=/absolute/path/to/prepared/delivery
SATELLITE_DELIVERY_SHA256=<trusted-delivery-catalog-sha256>
```

Pins берутся из принятой проверки выпуска, а не вычисляются автоматически из подключаемого каталога. [Правила подготовки и доверия](data/satellite.md#доставка-и-активация-а102) сохраняются. Оба каталога должны существовать: `create_host_path: false` запрещает создавать пустые директории. В PHP они доступны как `/satellite/runtime` и `/satellite/delivery` только для чтения; hash-проверки приложения не отключаются. Частичная настройка или некорректный формат pin останавливают PHP с понятной ошибкой при старте; `config --quiet` проверяет только Compose, а не полноту активации/существование данных. Отсутствующий явный bind отклоняет Docker при создании контейнера.

```bash
docker compose config --quiet
docker compose up -d --wait --wait-timeout 90
```

В экземпляре с актуальными значениями в `.env` последующие обычные Compose-команды читают те же значения: дополнительные `-f`, `--env-file` и override не нужны. Не задавать временные переопределения этих ключей в shell: они имеют приоритет над `.env`. Для отключения удалить только четыре satellite-ключа из `.env` и пересоздать PHP (`docker compose up -d --no-deps php`); данные сохраняются.

Перед изменением существующей активации сохранять локальную конфигурацию, `public/hot`, сведения о контейнерах и порядок возврата в новом приватном каталоге. Для существующей активации порядок возврата хранится в `data/backups/merge-compose-2026-11-11-01/RETURN.md`; каталог приватный, не публиковать. На этом ноутбуке Compose автоматически читает только описанный выше локальный override. Экспериментальные и резервные override хранить вне путей автопоиска. Существующие backup не перезаписываются.

## Выбор frontend-assets

Постоянный выбор задаётся адресной правкой `FRONTEND_ASSETS_MODE` в локальном `.env`. Значение по умолчанию — `dev`. Ключ уже есть в `.env.example`; в старый `.env` его нужно добавить один раз. Для существующего ключа:

```bash
# Выбрать dev (для build заменить последнее dev на build).
sed -i 's/^FRONTEND_ASSETS_MODE=.*/FRONTEND_ASSETS_MODE=dev/' .env
docker compose up -d --no-deps --wait --wait-timeout 90 php node nginx
```

- `FRONTEND_ASSETS_MODE=dev`: Node автоматически запускает `npm run dev -- --strictPort`, без `--host`; Laravel использует `public/hot`, Nginx ждёт Vite на 5173.
- `FRONTEND_ASSETS_MODE=build`: Node не запускает Vite, проверяет существующие `public/build/manifest.json` и assets и остаётся доступным для команд. Laravel выбирает manifest даже при оставшемся `public/hot` и прежнем Laravel config cache. Nginx ждёт проверки build-assets. Отсутствующая сборка — ошибка; автоматической пересборки нет.

Выбранный режим сохраняется после `docker compose up -d` и `docker compose restart node`. Перезапуск Node сам по себе не применяет новую правку `.env`: после выбора режима нужно пересоздание указанной командой. Build не означает публичный деплой или изменение `APP_ENV`.

Если сборки нет или её действительно нужно обновить, сначала сохранить существующий `public/build` в новый backup; затем явно выполнить `docker compose exec --user node node npm run build`. Команда заменяет сборку, но не меняет выбранный режим. Уже готовую сборку повторно не строить ради переключения. Ни build, ни переключение не удаляют `public/hot`.

## Первый запуск нового окружения

Нужны Docker и Compose v2. Команды выполнять из корня. Этот раздел относится к новому окружению: существующие `.env`, APP_KEY и volumes не заменять.

```bash
test -f .env || cp .env.example .env
```

Настроить параметры БД в локальном `.env`; на Linux при необходимости LOCAL_UID/LOCAL_GID по `id -u`/`id -g`. Зависимости нового checkout устанавливаются один раз до обычного запуска:

```bash
docker compose build
docker compose run --rm --no-deps php composer install
docker compose run --rm --no-deps --user node node npm ci
docker compose up -d
```

Только если APP_KEY пустой — `docker compose exec php php artisan key:generate`. Только для новой БД — `docker compose exec php php artisan migrate`. Автоматических миграций/импортов или переустановки зависимостей при обычном старте нет. После изменения package-lock зависимости обновляются отдельно; сборка production-assets не требуется для dev-режима.

Для первого запуска в `build`-режиме перед `up` требуется готовая сборка: после `npm ci` явно выполнить `docker compose run --rm --no-deps --user node node npm run build`. Для существующего окружения действует [правило сохранения сборки](#выбор-frontend-assets).

Миграции и установка меняют окружение; это не диагностические команды для уже работающего экземпляра. Без локального импорта профиль/поиск не получают выдуманных данных: подготовка наборов описана в [runbooks](data/README.md).

Приложение: [localhost](http://localhost); health endpoint — `/up`. Готовность окружения проверяется по [testing](testing.md), а не только по статусу контейнеров.

## Разработка и автомобильный пилот

Для подготовленного окружения используется сохранённый в `.env` режим assets:

```bash
docker compose up -d
```

В режиме `dev` Vite запускается как основной процесс Node-сервиса, без отдельного терминала и без `--host`. Порт 5173 фиксирован (`--strictPort`), готовность проверяется HTTP-healthcheck. Повторный `up -d` не запускает второй Vite. Логи: `docker compose logs -f node`. Изменения кода доступны через [localhost](http://localhost); `public/build` не перезаписывается.

Основной анализ использует четыре базовых сервиса и не требует routing-графов. Автомобильный OSRM сохранён в том же файле под профилем `routing`:

```bash
docker compose --profile routing up -d
```

Router не имеет опубликованного порта; внутренняя сеть, read-only snapshot, лимиты и guards сохранены. Перед включением требуется подготовленный проверенный набор по [runbook OSRM](data/local-routing.md). Обычный старт не удаляет и не останавливает ранее включённые опциональные контейнеры.

## Пеший пилот (opt-in)

ORS сохранён в едином файле под профилем `walking`. После отдельной подготовки/проверки снимка оба режима включаются так:

```bash
docker compose --profile routing --profile walking up -d --no-build --wait --wait-timeout 120
```

Профили не импортируют и не строят графы автоматически. Неизменяемый ORS snapshot, tmpfs для lock, ограничения ресурсов/сети и отключённое журналирование сохранены. Внешний ORS и ключ не используются. Подготовка и ограничения — [walking-backend](features/walking-backend.md). Дополнительные Compose YAML и override-симлинк не используются; routing/walking включаются профилями независимо от frontend-assets.

Правила распределения задач и передачи результата — в [AGENTS](../AGENTS.md#совместная-работа-codex-и-deepseek). Пользователь устанавливает Harness и подключает OpenRouter отдельно. Здесь нет подтверждения установки, настройки провайдера или успешного запуска модели.

В Web UI выбрать workspace `/home/daba/projects/web_gis`; для новой задачи дать обычное описание либо вставить поручение Codex. Убедиться, что агент получил корневой AGENTS.md; если это не видно в контексте, явно поручить прочитать его до действий. Дальше документы выбираются по задаче. Вернуться к Codex можно с исходным поручением и коротким итогом исполнителя: общим состоянием служат файлы и Git, перенос истории чата не требуется.

Перед первым поручением и после изменения версии, прав или окружения проверить настройки ниже. При неизменной конфигурации повторять всю подготовку для каждой задачи не требуется. Исполнитель и уровень ревью берутся из поручения или подготовленной задачи в плане; промежуточный запрос Codex для обычной задачи не обязателен.

- Выбрать разрешения `workspace-write` с политикой подтверждений `ask`, без `danger-full-access` и автоматического одобрения расширенного доступа. Это сочетание описано в [официальных permission presets](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/permission-presets.md); ограничения файловых операций и shell должны действовать вместе. Интерфейс слушает только loopback, без публикации в сеть.
- Ограничение записи не является ограничением чтения: [файловый sandbox Harness](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/fs/fs-sandbox/README.md) сохраняет доступное процессу чтение. AGENTS и `.gitignore` секреты технически не защищают. Исключить доступ модели и её shell к `.env`, ключам, домашним хранилищам авторизации и личным данным, не нужным задаче; разрешить только необходимые файлы и тестовые данные. Проверить фактическое применение ограничений, а не только выбранное название режима.
- При запуске от пользователя разработчика потенциально доступны его SSH-ключи, авторизация Codex, унаследованный SSH-agent, Docker socket и рабочие данные проекта. Не передавать процессу лишние credentials, SSH-agent и production-доступ. Ключ провайдера настраивать через предназначенные для него настройки Harness, не вставлять в поручение или репозиторий; не считать его скрытым от shell без проверки механизма хранения.
- Не давать безусловное разрешение на `docker`, произвольный shell или `sudo`: доступ к Docker daemon позволяет выйти за файловые ограничения через контейнеры и mounts. Не предоставлять доступ к production, рабочей БД и volumes как часть обычной задачи. Необходимые контейнерные проверки разрешать конкретными командами из [testing](testing.md), сохраняя запуск Node от пользователя `node`; повторное разрешение уже согласованной команды не нужно, если окружение, объём задания и политика доступа не изменились.
- Если установленная версия не обеспечивает нужных ограничений чтения и ресурсов, одного `workspace-write` недостаточно: до работы с секретами нужен отдельный ограниченный пользователь/окружение с безопасной копией исходников. Проверки, требующие недоступного Docker или рабочих credentials, выполняет пользователь и передаёт результат. Подготовка такой изоляции — отдельное поручение.

Не включать дополнительные MCP, skills, автоматические коммиты, публикацию или запуск других агентов ради передачи задачи. Конкретные права зависят от установленной версии; эта инструкция не заменяет проверку её sandbox и подтверждений.
