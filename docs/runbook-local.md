# Локальное окружение PlaceLens

Запуск приложения, OSRM и ORS в локальном окружении. Подготовку, импорт и миграции выполнять для явно выбранного окружения; существующие `.env`, ключи и volumes сохранять.

Команды ниже меняют окружение только при соответствующем поручении. Автомобильный режим обслуживает локальный OSRM, пеший — отдельный локальный ORS. API и ограничения — [поездки](features/trips.md).

## Стек и сервисы

PHP 8.4 / Laravel 13, PostgreSQL 16 / PostGIS 3.4, Vue 3 / TypeScript 6, Vite, MapLibre, Tailwind CSS 4 и shadcn-vue. Python ETL — одноразовая офлайн-подготовка, без постоянного сервиса. Точные зависимости — manifests/lock, версии контейнеров — Compose/Dockerfile; установленный пакет не означает реализованную функцию.

Базовые четыре сервиса: nginx, php, node, db. Nginx 80, Vite 5173 и БД 54325 опубликованы только на loopback. PHP использует `db:5432`; для IDE — `127.0.0.1:54325`, учётные данные из локального `.env`. Node-зависимости контейнера хранятся в named volume. Единственный Compose-файл — `docker-compose.yml`; Node сам запускает Vite от пользователя node, Nginx ждёт готовности dev-assets.

## Локальные спутники: рабочая активация

06.11.2026 А10.2 + И2 включены на [localhost](http://localhost): PHP читает pinned runtime А10.1 и доставку `krasnoyarsk-2024-2026-a10-2-v3` через read-only submounts; четыре `SATELLITE_*` заданы адресно в Compose, `.env` сохранён. Pins и совместимость шести выпусков/легенды сверены с принятым А10.2. [Правила подготовки и доверия](data/satellite.md#доставка-и-активация-а102).

`public/build` содержит актуальную production-сборку; прежний `public/hot` сохранён вне public, поэтому Laravel выбирает manifest. Vite остаётся запущен: его перезапуск может снова создать hot и переключить assets в dev-режим. Чтобы продолжать проверять production, сохранить вновь созданный hot вне public и проверить HTML на `/build/assets/`. Не отключать Node/БД и не пересоздавать другие сервисы ради активации.

Применение адресного изменения Compose: `docker compose up -d --no-deps --no-build php`, затем `docker compose exec -T php php artisan config:clear`. После замены PHP или Nginx location проверить `docker compose exec -T nginx nginx -t` и выполнить `docker compose exec -T nginx nginx -s reload`. Location satellite сохраняет application Cache-Control/Content-Type и отдаёт единственный no-referrer; access/error logging privacy не ослаблены.

Резервная копия — `data/backups/satellite-local-2026-11-06-01/`, точный возврат — `RETURN.md` внутри неё. Каталог содержит конфиденциальную исходную конфигурацию, не публиковать. Фактический smoke: рабочие Nginx/FPM POST/PNG, 6 дат, круги 200/1000 м, облака/край/null, POI=9 на контрольной публичной точке, безопасные заголовки/логи; браузер 390×844 и 1280×560, реальные слои/легенда/управление/быстрые смены. Контролируемые отказы проверены отдельно в изолированном стенде. Артефакты — `data/satellite/activation/2026-11-06-01/`; это локальная активация, не публичный деплой и не приёмка всего ядра/А13.

## Первый запуск нового окружения

Нужны Docker и Compose v2. Команды выполнять из корня. Этот раздел относится к новому окружению: существующие `.env`, APP_KEY и volumes не заменять.

```bash
test -f .env || cp .env.example .env
```

Настроить параметры БД в локальном `.env`; на Linux при необходимости LOCAL_UID/LOCAL_GID по `id -u`/`id -g`. Зависимости нового checkout устанавливаются один раз до обычного запуска:

```bash
docker compose build
docker compose run --rm --no-deps php composer install
docker compose run --rm --no-deps --user node node npm ci
docker compose up -d
```

Только если APP_KEY пустой — `docker compose exec php php artisan key:generate`. Только для новой БД — `docker compose exec php php artisan migrate`. Автоматических миграций/импортов или переустановки зависимостей при обычном старте нет. После изменения package-lock зависимости обновляются отдельно; сборка production-assets не требуется для dev-режима.

Миграции и установка меняют окружение; это не диагностические команды для уже работающего экземпляра. Без локального импорта профиль/поиск не получают выдуманных данных: подготовка наборов описана в [runbooks](data/README.md).

Приложение: [localhost](http://localhost); health endpoint — `/up`. Готовность окружения проверяется по [testing](testing.md), а не только по статусу контейнеров.

## Разработка и автомобильный пилот

Для подготовленного окружения достаточно одной команды:

```bash
docker compose up -d
```

Vite запускается как основной процесс Node-сервиса, без отдельного терминала и без `--host`. Порт 5173 фиксирован (`--strictPort`), готовность проверяется HTTP-healthcheck. Повторный `up -d` не запускает второй Vite. Логи: `docker compose logs -f node`. Изменения кода доступны через [localhost](http://localhost); `public/build` не перезаписывается.

Основной анализ использует четыре базовых сервиса и не требует routing-графов. Автомобильный OSRM сохранён в том же файле под профилем `routing`:

```bash
docker compose --profile routing up -d
```

Router не имеет опубликованного порта; внутренняя сеть, read-only snapshot, лимиты и guards сохранены. Перед включением требуется подготовленный проверенный набор по [runbook OSRM](data/local-routing.md). Обычный старт не удаляет и не останавливает ранее включённые опциональные контейнеры.

## Пеший пилот (opt-in)

ORS сохранён в едином файле под профилем `walking`. После отдельной подготовки/проверки снимка оба режима включаются так:

```bash
docker compose --profile routing --profile walking up -d --no-build --wait --wait-timeout 120
```

Профили не импортируют и не строят графы автоматически. Неизменяемый ORS snapshot, tmpfs для lock, ограничения ресурсов/сети и отключённое журналирование сохранены. Внешний ORS и ключ не используются. Подготовка и ограничения — [walking-backend](features/walking-backend.md). Дополнительные Compose YAML и override-симлинк больше не нужны; `.env` для выбора режима не изменяется.

## Проверки

[docs/testing.md](testing.md) — основное место команд, требований и побочных эффектов. Обычные frontend-команды: `docker compose exec --user node node npm run typecheck`, `docker compose exec --user node node npm test`; browser smoke — `docker compose exec --user node node npm run test:smoke` после [подготовки Chromium](browser-smoke.md).

PHP: `docker compose exec php composer test`; GIS: `docker compose exec php composer test:postgis` **только** с защищённой `web_gis_test`. Создание этой БД и особенности READ ONLY описаны в testing. Composer-обёртки очищают config, build меняет опубликованные assets, browser smoke пишет отчёты. Для задачи только на документацию полный запуск не требуется.

## Harness Web UI

Правила распределения задач и передачи результата — в [AGENTS](../AGENTS.md#совместная-работа-codex-и-deepseek). Пользователь устанавливает Harness и подключает OpenRouter отдельно. Здесь нет подтверждения установки, настройки провайдера или успешного запуска модели.

В Web UI выбрать workspace `/home/daba/projects/web_gis`; для новой задачи дать обычное описание либо вставить поручение Codex. Убедиться, что агент получил корневой AGENTS.md; если это не видно в контексте, явно поручить прочитать его до действий. Дальше документы выбираются по задаче. Вернуться к Codex можно с исходным поручением и коротким итогом исполнителя: общим состоянием служат файлы и Git, перенос истории чата не требуется.

Перед первым поручением и после изменения версии, прав или окружения проверить настройки ниже. При неизменной конфигурации повторять всю подготовку для каждой задачи не требуется. Исполнитель и уровень ревью берутся из поручения или подготовленной задачи в плане; промежуточный запрос Codex для обычной задачи не обязателен.

- Выбрать разрешения `workspace-write` с политикой подтверждений `ask`, без `danger-full-access` и автоматического одобрения расширенного доступа. Это сочетание описано в [официальных permission presets](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/permission-presets.md); ограничения файловых операций и shell должны действовать вместе. Интерфейс слушает только loopback, без публикации в сеть.
- Ограничение записи не является ограничением чтения: [файловый sandbox Harness](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/fs/fs-sandbox/README.md) сохраняет доступное процессу чтение. AGENTS и `.gitignore` секреты технически не защищают. Исключить доступ модели и её shell к `.env`, ключам, домашним хранилищам авторизации и личным данным, не нужным задаче; разрешить только необходимые файлы и тестовые данные. Проверить фактическое применение ограничений, а не только выбранное название режима.
- При запуске от пользователя разработчика потенциально доступны его SSH-ключи, авторизация Codex, унаследованный SSH-agent, Docker socket и рабочие данные проекта. Не передавать процессу лишние credentials, SSH-agent и production-доступ. Ключ провайдера настраивать через предназначенные для него настройки Harness, не вставлять в поручение или репозиторий; не считать его скрытым от shell без проверки механизма хранения.
- Не давать безусловное разрешение на `docker`, произвольный shell или `sudo`: доступ к Docker daemon позволяет выйти за файловые ограничения через контейнеры и mounts. Не предоставлять доступ к production, рабочей БД и volumes как часть обычной задачи. Необходимые контейнерные проверки разрешать конкретными командами из [testing](testing.md), сохраняя запуск Node от пользователя `node`; повторное разрешение уже согласованной команды не нужно, если окружение, объём задания и политика доступа не изменились.
- Если установленная версия не обеспечивает нужных ограничений чтения и ресурсов, одного `workspace-write` недостаточно: до работы с секретами нужен отдельный ограниченный пользователь/окружение с безопасной копией исходников. Проверки, требующие недоступного Docker или рабочих credentials, выполняет пользователь и передаёт результат. Подготовка такой изоляции — отдельное поручение.

Не включать дополнительные MCP, skills, автоматические коммиты, публикацию или запуск других агентов ради передачи задачи. Конкретные права зависят от установленной версии; эта инструкция не заменяет проверку её sandbox и подтверждений.

## Остановка

```bash
docker compose stop
```

Данные БД остаются в volume `postgres_data`. Остановка не является очисткой volumes, исходников или routing runtime.
