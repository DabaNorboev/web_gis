# Схема данных

Миграции создают транспортную схему PostgreSQL/PostGIS. Импортер и транспортный HTTP API реализованы. Запуск — в [инструкции импорта](transport-import.md).

| Таблица | Содержимое |
|---|---|
| `dataset_imports` | Источник/набор, версия, даты, SHA-256 входа и конфигурации, статус, результат, активность |
| `transport_stops` | ID остановки в источнике, название, адрес, точка, `raw_data`, связь с импортом |
| `transport_routes` | Исходный ключ, `mode`, `ref`, `raw_data`, связь с импортом; без геометрии трассы |
| `transport_stop_routes` | Уникальная связь остановки и маршрута одного снимка |

## Снимки и идентификаторы

- Логический ключ остановки: `(source, dataset_key, source_id)`. Для CSV `source_id` — строковый `id`; стабильность между версиями не подтверждена. Для OSM в ключ входит тип: `node/123`, `way/123`, `relation/123`.
- В снимке уникален `(dataset_import_id, source_id)`. Внутренний `id` меняется между снимками и не является постоянным внешним ID.
- Ключ маршрута — `mode:ref`, например `bus:7`. Виды: `bus`, `trolleybus`, `tram`, `unknown`; уникален также `(dataset_import_id, mode, ref)`. Направления одной линии не считаются разными маршрутами.
- Новый импорт создаёт отдельные строки. Составные внешние ключи запрещают связи между снимками; удаление связанных строк ограничено.
- На `(source, dataset_key)` допускается один активный успешный импорт. Загрузка строк и переключение активного снимка атомарны; при ошибке старый снимок остаётся активным, попытка получает `failed`.
- Повтор успешного входа определяется по SHA-256 файла и конфигурации (64 строчных hex-символа); частичный уникальный индекс запрещает дубликаты. Неудачу можно повторить. Повтор исторического входа не реактивирует его.
- Для нескольких SQL-расчётов одного запроса фиксировать активный `dataset_import_id` один раз. Исчезнувшие объекты исключаются из текущей выдачи, история сохраняется; это не доказывает закрытие объекта. Очистка истории требует отдельного решения.

## Даты и качество

`source_version`/`source_updated_at` описывают исходник; `observed_at` — известную дату наблюдения. Дата публикации или импорта не заменяет наблюдение. Время обработки — `started_at`/`finished_at` (`timestamptz`); обмен датами — UTC.

Статусы: `running` (без завершения), `succeeded`, `failed` (завершение не раньше начала). `row_count` — число принятых остановок, `null` при неизвестном результате. Статистика и предупреждения — `result`, причина сбоя — `error_message`. Исходные поля остаются в `raw_data`. Неизвестный тип и пустой перечень маршрутов не означают ноль маршрутов.

## GIS и проверки

- Точки — непустые двумерные `geometry(Point, 4326)`. Порядок: `lon, lat`; диапазоны ±180/±90. Ошибочные координаты не подменяются; отбор города выполняется границей.
- Расстояния/радиусы — метры через `geom::geography`. Для площадей — `ST_Transform` в EPSG:32646 (WGS84 / UTM 46N); формулу и SRID фиксировать для показателя.
- GiST-индексы созданы отдельно для `geom` и выражения `geom::geography`. Индекс geometry не заменяет индекс выражения. Пример поиска: `ST_DWithin(geom::geography, ST_SetSRID(ST_MakePoint(:lon, :lat), 4326)::geography, 500)`.
- Миграция подключает PostGIS; её откат сохраняет расширение. Применение: `docker compose exec php php artisan migrate`.
- GIS-тесты: `tests/Integration`, отдельная `web_gis_test`, запуск `sh scripts/init-test-db.sh` и `docker compose exec php composer test:postgis`. Проверяются ограничения, индексы, метры, снимки и откат/повтор миграций в изолированной тестовой схеме. Обычные тесты используют SQLite; предметная GIS-схема требует PostgreSQL.

[PostGIS ST_DWithin](https://postgis.net/docs/ST_DWithin.html).
