# Схема данных: первый транспортный импорт

Схема создаётся миграциями Laravel в PostgreSQL/PostGIS. Импортер и атомарная публикация снимков реализованы: [инструкция](transport-import.md). HTTP API ещё не реализован.

## Таблицы

| Таблица | Назначение |
|---|---|
| `dataset_imports` | Источник, версия, даты, контрольные суммы, настройки, результат и состояние импорта |
| `transport_stops` | Остановки конкретного снимка: ID в источнике, название, адрес, точка и исходная запись |
| `transport_routes` | Номер маршрута и вид транспорта конкретного снимка; исходные сведения |
| `transport_stop_routes` | Связи остановок с маршрутами одного и того же снимка |

Один импорт транспортного набора содержит остановки, маршруты и связи. Геометрия маршрутов отсутствует: официальный CSV содержит список номеров, но не трассы движения.

## Проверенный формат официального набора

Исходный файл — UTF-8 CSV, разделитель полей — запятая. Колонки: `id`, `name`, `type_transport`, `num_route`, `address`, `the_geom_lon`, `the_geom_lat`. В скачанной версии 3 791 запись; `id` заполнены и уникальны. Долгота и широта хранятся отдельными числовыми полями, EPSG:4326. В региональном файле две записи без координат; импортер должен учитывать отклонённые строки, а не создавать для них фиктивные точки.

Отдельных ID маршрутов и таблицы связей в файле нет. `num_route` содержит строку с перечнем маршрутов; в проверенных записях встречаются, например, `85,99`, `7т,8т,...`, `4тр,7тр`. Тип транспорта и написание обозначений неоднородны. Разбор токенов, сокращений и сопоставление вида транспорта реализованы и проверяются интеграционными тестами с сохранением оригинала в `raw_data`. Схема не предполагает, что номер без уточнения вида однозначно идентифицирует маршрут.

## Идентификаторы и повторный импорт

- `source` — постоянный машинный ключ источника. `dataset_key` — набор и область обработки, например `transport_stops:krasnoyarsk`.
- Логическая идентичность остановки — `(source, dataset_key, source_id)`. Для официального CSV сохраняется `id` как строка; стабильность этих ID между версиями ещё нужно проверить. Для OSM тип объекта входит в ID: `node/123`, `way/123`, `relation/123`.
- Внутри снимка уникален `(dataset_import_id, source_id)`. В другом снимке тот же исходный ID допустим. Внутренний `id` строки не является постоянным внешним идентификатором остановки.
- Маршрут — номер в пределах вида транспорта: `bus`, `trolleybus`, `tram`, `unknown`. Например, автобус №7 и трамвай №7 — разные маршруты. Для официального CSV `source_id` маршрута формируется как `bus:7`; уникальны и исходный ключ, и `(dataset_import_id, mode, ref)`.
- Разные направления/варианты одной линии не являются отдельными маршрутами в этой схеме. При будущей обработке OSM их нужно нормализовать до номера и вида транспорта, сохраняя исходные сведения.
- Неизвестный вид транспорта не угадывается. Отсутствующий список маршрутов не означает ноль действующих маршрутов.

`checksum_sha256` — SHA-256 исходного файла. `configuration_sha256` — SHA-256 канонической JSON-конфигурации обработки. Конфигурация содержит версию импортера, границу/её контрольную сумму, фильтры и правила нормализации. Меняется обработка — меняется её контрольная сумма. Оба хеша имеют 64 строчных шестнадцатеричных символа; их соответствие содержимому проверяет импортер.

Повторный запуск сначала ищет успешный импорт с теми же `(source, dataset_key, checksum_sha256, configuration_sha256)` и использует готовый снимок. Частичный уникальный индекс дополнительно запрещает два успешных импорта одного входа. Неуспешные попытки можно повторять. Изменённая конфигурация допускает новую обработку того же файла.

## Даты и результат

- `source_version` и `source_updated_at` описывают версию/обновление источника.
- `observed_at` — дата наблюдения или снимка, только когда она известна. Дата изменения страницы/файла не подставляется вместо неё.
- `started_at`, `finished_at` — время обработки, `timestamp with time zone`. В приложении даты обмена — UTC.
- Состояния: `running`, `succeeded`, `failed`. У запущенного импорта нет времени завершения; у завершённого оно не раньше начала.
- `row_count` — число принятых остановок; неизвестное число допускает `NULL`. `result` — JSON с числом прочитанных, принятых, исключённых и отклонённых записей, количеством маршрутов/связей и предупреждениями. `error_message` — причина неудачи.
- Оригинальные значения сохраняются в `raw_data`; нормализованные поля не заменяют исходную запись.

## Публикация и исчезнувшие объекты

Остановки не перезаписываются глобальным upsert. Новый файл создаёт отдельный снимок. Upsert при загрузке действует внутри снимка по `(dataset_import_id, source_id)`; связь уникальна по паре остановки и маршрута. Составные внешние ключи запрещают связи между разными снимками.

Импортер должен выполнять следующие действия:

1. Проверить идентичность входа, зарегистрировать попытку и подготовить новый снимок.
2. В транзакции загрузить/проверить остановки, маршруты и связи.
3. Сериализовать публикации одного `(source, dataset_key)` блокировкой, повторно проверить вход и снять `is_active` с предыдущего снимка.
4. В той же транзакции отметить новый снимок `succeeded`, сохранить результаты и установить `is_active = true`.
5. При ошибке откатить загрузку/переключение, сохранить состояние `failed` и причину вне откатившейся транзакции. Старый снимок остаётся активным.

Частичный уникальный индекс допускает один активный снимок на источник и набор. Активным может быть только успешный импорт. Ограничения БД поддерживают этот протокол, но не заменяют код импортера и проверки полноты. Пустой/аномально уменьшившийся набор нельзя автоматически публиковать без проверки.

Пользовательские запросы выбирают `is_active = true`. Для нескольких расчётов одного запроса сначала фиксируются ID активных импортов, затем все запросы используют эти ID: переключение между SQL-запросами не смешивает версии. Старые снимки сохраняются.

Объект, отсутствующий в новом полном снимке, исчезает из текущей выдачи, оставаясь в истории. Отсутствие объекта не доказывает его закрытие. Физическое удаление истории и очистка неудачных снимков — отдельное решение. Внешние ключи ограничивают удаление связанных записей.

## GIS-соглашения

- `transport_stops.geom`: обязательная двумерная непустая `geometry(Point, 4326)`, WGS84.
- Порядок координат — **longitude, latitude**: `ST_MakePoint(lon, lat)`; в JSON — явно `lon` и `lat`.
- Допустимые диапазоны: долгота `[-180, 180]`, широта `[-90, 90]`. При импорте дополнительно проверяются граница города и правдоподобность координат. Ошибочные точки исключаются с причиной, координаты не придумываются.
- Для расстояний и радиусов используется `geom::geography`; единица — метр. Пример: `ST_DWithin(geom::geography, ST_SetSRID(ST_MakePoint(:lon, :lat), 4326)::geography, 500)`.
- Предусмотрены два GiST-индекса: на `geom` для пространственного отбора геометрий и на выражение `geom::geography` для метрических запросов. Индекс геометрии сам по себе не заменяет индекс выражения.
- Расстояния в градусах и площади EPSG:4326 не выдаются как метры/м². Для будущих расчётов площади в Красноярске используется локальная метрическая проекция EPSG:32646 (WGS84 / UTM zone 46N), через `ST_Transform`; формула и SRID фиксируются с конкретным показателем.
- PostGIS подключается отдельной миграцией. При откате расширение сохраняется: оно может использоваться другими таблицами.

Документация: [ST_DWithin](https://postgis.net/docs/ST_DWithin.html), [ограничения PostgreSQL 16](https://www.postgresql.org/docs/16/ddl-constraints.html).

## Исходные файлы и проверки

Сырые файлы хранятся в игнорируемой `data/raw/<dataset>/<version>/`; отчёты подготовки — в `data/reports/`. URL, хеш файла, дата версии и способ получения фиксируются при реализации первого импортера. Первый источник остановок — официальный CSV; автоматического объединения с OSM нет.

Применение схемы:

```bash
docker compose exec php php artisan migrate
```

Проверки работают только в `web_gis_test` и откатывают тестовые записи. Они проверяют тип/SRID/диапазоны координат, метры и пространственные индексы, дубликаты, целостность связей, состояния импорта, идемпотентность успешного входа и атомарное переключение снимков. Откат/повторное применение GIS-миграций проверяется в изолированной схеме тестовой БД.

```bash
sh scripts/init-test-db.sh
docker compose exec php composer test:postgis
```

GIS-миграции требуют PostgreSQL/PostGIS. Обычные unit/feature-тесты без GIS используют SQLite; тесты, которым нужны предметные миграции, запускаются в PostGIS-наборе.
