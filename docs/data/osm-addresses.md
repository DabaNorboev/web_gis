# Локальный импорт адресов OSM

`osm_addresses`, офлайн-команда импорта и атомарные снимки. [Локальный API поиска и autocomplete](../features/address-search.md) реализованы; режим [«Остановки рядом»](transport-import.md) сохранён.

## Исходник

Для первого импорта выбран сохранённый JSON адресных объектов Красноярска из [Overpass](https://overpass-api.de/), с геометрией и OSM-метаданными. Запрос выполняется только при подготовке снимка, не при поиске адреса. Для полного Stage 4 доступен [PBF Красноярского края](https://download.openstreetmap.fr/extracts/russia/siberian_federal_district/), но он требует отдельного чтения/обрезки; не скачивался: для зданий использован [отдельный JSON](osm-buildings.md).

- Файлы: `data/raw/osm_addresses/2026-10-18/{addresses.json,addresses.overpassql,manifest.json,download.py}`.
- Состояние базы OSM: `2026-10-18T08:33:06Z`; это версия снимка, не дата наблюдения каждого дома. `observed_at` остаётся `null`.
- SHA-256 JSON: `7da53acb2051f66f4e8778daf4514f7b0ba7aa07d9b804e72ff7e0d5abd63b76` (35 471 579 байт). Хеш запроса и время получения — в manifest.
- Отбор: area relation `1157393`, затем проверка по ранее сохранённому GeoJSON городского округа. Это согласованный охват проекта, а не гарантия границ населённого пункта: `addr:city` не затирать значением «Красноярск».
- Все сырые файлы и отчёты находятся в игнорируемом `data/`. Повтор запроса даёт новый снимок, а точный повтор импорта использует сохранённый файл и его хеш.

## Проверка снимка

Перед импортом сверить SHA-256, структуру и полноту геометрии. Предварительная сборка через `ST_BuildArea` не разрешает публиковать неполную или невалидную геометрию.

Текстовый адрес не уникален: node/way/relation могут иметь одинаковые подписи. Сохранять исходные `addr:street` и `addr:place`, буквенные/дробные номера и дополнительные поля; не разрезать номер по `/`, не угадывать улицу и не разбирать `addr:full` автоматически. [Формат адресов OSM](https://wiki.openstreetmap.org/wiki/Key:addr).

## Таблица `osm_addresses`

Одна строка — адресный OSM-объект в конкретном снимке; канонические адреса и объединение дублей пока не объявляются.

| Поля | Назначение |
|---|---|
| `id`, `dataset_import_id` | Внутренний ключ и FK на существующий журнал снимков |
| `osm_type`, `osm_id`, `osm_version`, `osm_updated_at` | Тип node/way/relation, положительный OSM ID, версия и время правки |
| `street`, `place`, `house_number`, `locality`, `postcode` | Разрешённые адресные части; номер — текст, locality/postcode могут быть неизвестны |
| `label` | Подпись из известных частей, без выдуманного города |
| `source_geom` | Исходная Point/Polygon/MultiPolygon, EPSG:4326; не полный слой зданий |
| `geom`, `point_method` | `geometry(Point,4326)` для анализа; `osm_node` либо `point_on_surface` |
| `raw_data` | Исходные теги/метаданные и происхождение разрешения улицы, ссылки на associatedStreet |

Ограничения: уникальность `(dataset_import_id, osm_type, osm_id)`, допустимый тип, положительные ID/версии, непустые номер и улица либо место, валидные непустые 2D-геометрии с допустимыми координатами. GiST для `geom` и `source_geom`; индекс по паре OSM type/ID для открытия объекта. В Stage 5 добавлены вычисляемый `search_text` и GIN/`pg_trgm`; правила — в [описании поиска](../features/address-search.md).

Для node сохраняется исходная точка. Для polygon/multipolygon — [ST_PointOnSurface](https://postgis.net/docs/ST_PointOnSurface.html) в PostGIS: точка внутри контура, не координата входа. Обмен — lon/lat; метод сохраняется. Связь со зданием не должна дублировать его как независимый новый OSM-объект.

## Правила импорта и дальнейший поиск

- Использовать `dataset_imports`: source=`OpenStreetMap`, dataset_key=`addresses`; отдельный активный атомарный снимок, SHA-256 входа и конфигурации (с хешем границы), версия правил — 1. Время базы OSM — `source_updated_at`/`source_version`, время правки объекта — `osm_updated_at`, `observed_at: null`.
- Импортировать структурированные адреса с номером и улицей/местом. Приоритет — собственный `addr:street`, затем `addr:place`, затем однозначная именованная associatedStreet; всё происхождение сохранять. Кандидаты без необходимых частей — в отчёт пропусков, не дополнять догадками. Несогласованные теги отмечать предупреждениями.
- Закрытость, полноту геометрии, отверстия и ошибки валидности проверять до публикации; не исправлять молча. Геометрию/населённый пункт определять на backend при импорте.
- Не объединять одинаковые подписи в БД и не импортировать POI как категории. В Stage 5 реализованы ранжирование и осторожное устранение повторов выдачи: адресный контур здания предпочтительнее совпадающего POI/входа внутри него; одинаковые адресные части теперь сгруппированы в одну подсказку, при этом объекты остаются отдельными и выбираются на карте; разные населённые пункты не объединяются. Вторичные адреса сохранить для последующей нормализации.
- Внешний ID для поиска/профиля — например `osm:way:403615986`, с типом и числом; внутренний `id` строки меняется между снимками. Исчезнувший объект не подменять похожим адресом.
- CLI `ImportOsmAddresses` делегирует работу `OsmAddressImporter`, `OsmAddressReader` и `OsmAddressGeometry`. Валидатор границы `Services/Gis/GeoJsonBoundary` общий с импортом остановок. GIS-проверки, повторы и откат сбоя — в `web_gis_test`.

## Запуск

Из корня проекта, без сетевых запросов. На сохранённом JSON около 34 МиБ используется лимит памяти 512 МиБ только для CLI-процесса: весь Overpass-документ читается в память. Это не потоковый импортер произвольного PBF.

```bash
docker compose exec php php artisan migrate

docker compose exec php php -d memory_limit=512M artisan osm:import-addresses \
  data/raw/osm_addresses/2026-10-18/addresses.json \
  --boundary=data/raw/boundaries/krasnoyarsk/2026-10-07/boundary.geojson \
  --dry-run --report=data/reports/osm_addresses_import/2026-10-18/dry-run.json
```

Для публикации повторить без `--dry-run`, например с `--report=data/reports/osm_addresses_import/2026-10-18/import.json`. `--dry-run` не меняет строки адресов и журнал импорта; при `--report` записывает локальный отчёт. Точный повтор успешного файла/конфигурации возвращает `skipped`, исторический снимок повторно не активируется. Изменение входа или границы создаёт новый снимок; исчезнувшие объекты остаются только в истории. Снижение количества более чем на 20% блокирует публикацию; после проверки отчёта допускается `--allow-large-drop`. Пустой результат не публикуется.

Подготовка идёт во временной таблице, вставка адресов и смена активного снимка — в одной транзакции. Ошибка публикации оставляет прежний снимок активным, попытка получает `failed`. Файл/структура JSON и граница проверяются до создания записи попытки. Одновременные публикации источника блокируются advisory lock. Снимок остановок не переключается.

Кольца составляются по точному совпадению концов без округления и замыкания разрывов. Роли outer/inner обязательны; отверстие должно однозначно принадлежать внешнему кольцу. Вложенные отношения сейчас не поддерживаются и не игнорируются. Невалидная геометрия не исправляется через MakeValid/BuildArea. Для отбора граница должна покрывать **точку анализа**; контур не обрезается, выход части контура за границу отмечается предупреждением.

## Проверки

GIS-тесты в `web_gis_test` проверяют координаты, отверстия, пропуски, ограничения, повторы, историю снимков, dry-run, защиту уменьшения и откат публикации. Обратимость миграции — только в изолированной тестовой схеме. Запуск: `docker compose exec php composer test:postgis`.

## Здания

Полный отдельный снимок зданий, аудит и атомарный импорт `osm:import-buildings` описаны в [инструкции зданий](osm-buildings.md). Адресный набор и поиск остаются независимыми.
