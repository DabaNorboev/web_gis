# Web GIS — локальная спецификация

## Продукт и архитектура

PlaceLens помогает людям, которые ищут жильё в Красноярске, сравнить несколько адресов по повседневному окружению и важным лично для них местам.

Главная аудитория — люди, выбирающие жильё. Риэлторы — дополнительная аудитория: отчёт для клиента и специальные сценарии рассматриваются позже. Сервис описывает место вокруг жилья; он не оценивает состояние квартиры, юридическую чистоту, качество подъезда или цену без отдельных надёжных источников.

Первый законченный продукт — сравнение выбранных адресов по одинаковым критериям на доступных локальных данных. Профиль одного адреса — основа сравнения, а не отдельный продуктовый режим. Персональные места входят в общее видение; маршруты к ним и подбор районов проверяются после базового сравнения и не являются условием его выпуска. Анализ и сравнение в первой версии доступны без обязательной регистрации. Личный кабинет, история просмотров и шаблоны нужны для сохранения вариантов и повторных сравнений; они не блокируют первый анализ.

Разделы первого профиля:

| Вопрос пользователя | Состав и ограничения |
|---|---|
| Что рядом | Остановки, парки, зелёные территории и вода. Расстояния пока по прямой; общественный доступ и удобный вход не гарантируются. |
| Как устроено окружение | Близость крупных дорог и железнодорожных путей. Расстояние не доказывает шум или загрязнение. |
| Насколько много застройки вокруг | Только после проверки понятной методики: что считается зданием, как исключаются части/повторы и рассчитывается доля площади. Наличие импортированных контуров не означает готовность показателя. |

Поиск районов по работе, учёбе и другим личным точкам — следующий возможный сценарий после проверки сравнения. Магазины, аптеки, школы и другие POI добавляются после выявления потребности и выбора источников. Спутниковая история и воздух отложены: спутники требуют конкретного пользовательского вопроса и успешного PoC; воздух — подтверждённых покрытия, актуальности и пригодности для сравнения адресов.

Показывать независимые показатели с источником, датой и качеством. Единого субъективного рейтинга (`78/100`) нет. Недостаток данных сообщать явно, значения не придумывать.

Модульный монолит, offline-first для базовой аналитики: подготовленные геоданные — в PostGIS, бизнес-логика и REST API — Laravel, UI — Vue, тяжёлая GIS/raster-обработка — Python ETL. Базовые профиль и сравнение работают без внешних аналитических API; подложка карты может требовать интернет. API организаций и времени в пути сначала испытываются на небольшой выборке отдельным заданием, после проверки потребности, покрытия, стоимости и условий хранения/показа результатов. Недоступность дополнительного источника не скрывает локальные показатели. Тяжёлые операции выполняются заранее.

| Источник | Назначение и ограничения |
|---|---|
| OpenStreetMap | Адреса, здания, дороги, железная дорога, зелень, вода, геометрия окружения. Локальный импорт, без live Overpass на каждый запрос. |
| Официальные остановки | Ближайшая остановка и расстояние, остановки/уникальные маршруты в радиусе. Локальный набор; OSM автоматически не подмешивать. |
| Аварийные дома | Этап отложен, не блокирует первое сравнение. При реализации — официальный локальный набор: количество, ближайший объект, расстояние и список рядом. Контекст, без рейтинга. |
| air.krasn.ru | Отложенный кандидат: сначала проверить доступность данных, покрытие, актуальность и пригодность для сравнения адресов. При реализации — ближайший пост/расстояние, PM2.5, история; далёкий пост или мало данных → `INSUFFICIENT_DATA`; недоступность не ломает сервис. |
| Sentinel-2 | Кандидат для отдельного исследования истории растительности после подтверждения пользы. При реализации — офлайн-подготовка NDVI/растительности; скачивание сцен и raster-обработка внутри HTTP запрещены. |

## Стек и окружение

- Backend: PHP 8.4, Laravel 13, REST API, PostgreSQL 16 / PostGIS 3.4.
- Frontend: Vue 3, TypeScript 6 (совместимость с `vue-tsc`, без TS 7), Vite, MapLibre GL JS, Apache ECharts, Tailwind CSS 4, shadcn-vue (`reka-nova`, neutral).
- ETL при реальной необходимости: Python 3.12, Pandas, GeoPandas, Shapely, Rasterio, GDAL, PyProj, psycopg.
- Docker Compose + Nginx; только четыре сервиса:

| Сервис | Назначение |
|---|---|
| `nginx` | `nginx:1.27-alpine`, HTTP, PHP-запросы → `php:9000` |
| `php` | Custom PHP-FPM image, Composer, Laravel, PostgreSQL extensions; без Node.js |
| `node` | `node:22-bookworm-slim`, npm/Vite/Vue/TypeScript |
| `db` | `postgis/postgis:16-3.4`; внутри `db:5432`, с хоста `127.0.0.1:54325` |

Порты Nginx (80), Vite (5173) и БД опубликованы только на `127.0.0.1`. Laravel: `DB_HOST=db`, `DB_PORT=5432`. Первый запуск и проверки — в README; существующие `.env`, ключ и volumes не перезаписывать.

```bash
docker compose up -d
docker compose exec php bash
docker compose exec node bash
# В node-контейнере: npm ci, npm run dev (без --host)
```

Фронтенд — `resources/js/{components,layouts,pages,composables,api,types,utils}`; точка входа пока `app.js`. shadcn-vue: `components.json`, `components/ui`, `utils/cn.ts`, алиас `@` → `resources/js`. Проверка: `npm run typecheck`; добавление UI: `npm run ui:add -- <name>`, только в `node`. Соглашения — `docs/frontend-structure.md`. Реализована главная PlaceLens: компактная шапка, боковая панель с объяснением/поиском и карта справа; на мобильных панель над картой. Подключён транспортный анализ по точке. Поиск, профиль адресного объекта и сравнение двух адресов подключены к локальному API; общий каркас — PlaceLayout.

## Модель показателя и GIS

С первого импорта/API хранить происхождение и доступность. Поля результата: `key`, `value`, `unit`, `source`, `dataset_import_id`, `observed_at`, `calculated_at`, `quality`:

- `method`: `DIRECT`, `DERIVED`, `PROXY`; `null`, если результата нет.
- `availability`: `AVAILABLE`, `INSUFFICIENT_DATA`, `UNAVAILABLE`.
- `freshness`: `CURRENT`, `STALE`, `UNKNOWN`.
- `reason`: понятная причина качества или отсутствия результата.

Свойства независимы: вычисленный результат может быть устаревшим. Без результата `value: null`, не фиктивный ноль. Неизвестная дата данных → `observed_at: null`, `freshness: UNKNOWN`. Время публикации/импорта/расчёта не заменяет наблюдение. Пороги актуальности и достаточности задаются для каждого источника и показателя; даты обмена — UTC.

Geometry и координаты обмена — EPSG:4326, порядок `lon, lat`. Остановки — непустые 2D `geometry(Point,4326)`. Расстояния/радиусы — метры через `geography` или документированную метрическую проекцию, не градусы geometry. Площади — в подходящей проекции (для Красноярска согласована EPSG:32646); формулу/SRID документировать при реализации. GiST должен соответствовать запросу: для `geom::geography` нужен индекс выражения.

Импорт хранит источник, известную дату наблюдения, версию/хеш входа, время и результат обработки. Объекты связаны с импортом и исходным ID; OSM ID включает `node/way/relation`. Ключи повторной загрузки и поведение исчезнувших объектов определять для каждого источника. Сырые файлы: `data/raw/<dataset>/<version>/`, отчёты: `data/reports/`; `data/` не коммитится. URL/хеши/способ получения документировать.

## Roadmap

Переход между стадиями требует отдельного задания. Нумерация сохраняется как идентификаторы областей работ и не задаёт очерёдность. В частности, Stage 18 входит в первый законченный продукт после готовности профиля; Stage 11 и 14–17 его не блокируют. Проверки и исправления текущего задания входят в его объём.

| Stage | Результат |
|---|---|
| 0 — Infrastructure | Воспроизводимое Docker/Laravel/Vite/PostGIS-окружение по README на новом `.env` и volumes. |
| 1 — Схема БД | Миграции `dataset_imports`, `transport_stops`, `transport_routes`, `transport_stop_routes`; GIS-соглашения, индексы, идентификаторы, атомарность и тесты в `web_gis_test`. |
| 2 — Остановки | Импорт названия, координат, маршрутов, исходных данных и даты импорта; по точке — ближайшая остановка/расстояние, остановки и уникальные маршруты в 500 м. Цепочка dataset → DB → Laravel → JSON. |
| 3 — Аварийные дома | `emergency_houses`: импорт, количество в 500 м, ближайший/расстояние, список ближайших. |
| 4 — OSM import | Локальный импорт только адресов, зданий, дорог, железной дороги, зелени и воды; запросы окружения через PostGIS. |
| 5 — Поиск адреса | Нормализация, fuzzy search через `pg_trgm`; `GET /api/v1/addresses/search?q=...` возвращает ID, label, lat/lon. |
| 6 — Окружение | В 500 м: парки, зелень, вода, крупные дороги и железная дорога; точные формулы/состав согласовать в задании. Застройка (число/доля площади) — после проверки методики. Учитывать покрытие и независимые признаки парка/растительной территории. |
| 7 — Профиль | `GET /api/v1/addresses/{id}/profile`: address, environment, transport как основа сравнения; работает без внешних аналитических API и обязательной регистрации. Аварийные дома подключаются только после Stage 3 и не блокируют профиль. Воздух/спутники отложены. |
| 8 — Data Quality | Унифицировать уже существующую модель качества; пороги, причины отсутствия, независимость метода/доступности/актуальности. |
| 9 — Frontend shell | Общий каркас PlaceLens, главная, реальный поиск/autocomplete, профиль `/address/:id`, состояния данных и адаптивность. Подэтапы 9.1–9.4 описаны ниже. |
| 10 — Карта и категории | MapLibre layers, синхронизация карты с профилем, легенда и выбор доступных категорий. Состав категорий определяется источниками; не множество DOM-маркеров. |
| 11 — Воздух | Отложен до проверки достаточности близких измерений, актуальности и пригодности для сравнения. При отдельном задании — `air_stations`, `air_measurements`, provider, локальное хранение, ближайший пост, fallback и блок PM2.5. |
| 12 — Scheduler | Только после реальной задачи (например, `air:sync`): контейнер `scheduler` с тем же PHP image, `php artisan schedule:work`. |
| 13 — Python ETL | Контейнер только при первой реальной задаче: GIS-подготовка, затем спутники. Может понадобиться раньше, в Stage 2–4, в рамках согласованного задания. |
| 14 — Sentinel-2 PoC | Отдельное отложенное исследование после определения полезного вопроса: маленькая область, несколько лет, проверка пригодности до полного pipeline. Первое сравнение адресов не блокирует. |
| 15 — Satellite pipeline | Сцены → cloud/shadow/snow mask → B4/B8 → NDVI → летняя медианная композиция → агрегация по сетке → PostGIS; после успешного PoC. |
| 16 — Satellite grid | Сетка около 100×100 м: `satellite_cells`, `satellite_year_stats`; year, ndvi_median, vegetation_share, valid_pixel_share, scene_count. |
| 17 — Машина времени | `GET /api/v1/addresses/{id}/satellite-history`: история растительности, график/изменения, пропущенные годы, качество, покрытие и число сцен. |
| 18 — Сравнение | Первый законченный сценарий: сравнение выбранных адресов по одинаковым локальным показателям профиля, без обязательной регистрации. Минимум два адреса; лимит и URL согласовать в задании (для пары возможен `/compare?left={id}&right={id}`). Воздух, спутники, POI и аккаунт не являются зависимостями. |
| 19 — Методология | Собрать публичное описание источников, формул, радиусов, дат, ограничений и правил качества, документированных при реализации. |
| 20 — Итоговая проверка | Ручная сверка минимум 10 реальных адресов и сквозная проверка реализованных пользовательских сценариев на desktop/mobile. Автоматические тесты — на каждом этапе. |
| 21 — Вход и регистрация | Будущий этап: регистрация, вход, выход, восстановление доступа; детали способа входа согласовать перед реализацией. |
| 22 — Личное пространство | Личный кабинет: сохранённые адреса, история просмотров и настройки аккаунта. Детали и правила хранения уточнить перед реализацией. |

### Ближайший порядок работ — решение 20.10.2026

1. Исправить достоверность текущего сценария (Stage 5, 8): поиск с названием города, нормализацию контекста без подмены исходного населённого пункта, явное состояние вне покрытия. Для радиусных расчётов разделить границу сервиса и границу загрузки с буфером не меньше максимального радиуса; отдельно определить охват поиска ближайшего объекта. В рамках исправления поиска проверить замеры и перенос повторяемых пространственных сопоставлений в подготовку снимка.
2. Проверить и завершить пригодность зелени/воды для показателей (Stage 4, 6). Импорт уже выполнен; это корректировка классификации и проверка данных, а не повторное скачивание по умолчанию. Парк и растительная территория — независимые признаки одного объекта. Проверить Татышев, Гвардейский парк, наложения, границы и ограничения доступа.
3. Собрать профиль и сравнение (Stage 6–10, 18) с одинаковыми критериями, радиусами, источниками, датами, качеством и явными пропусками. Застройку включать только при проверенной методике; методологию и проверки делать вместе с функцией.
4. Проверить сценарий на людях, реально выбирающих жильё; выяснить, каких сведений не хватает и что влияет на выбор. По результатам определить необходимость POI, сохранений и повторных сравнений.
5. Отдельным заданием испытать API организаций и времени в пути на небольшой выборке. Выбор поставщика и интеграция не утверждены. Персональный подбор областей, воздух и спутники требуют собственных решений после проверки пользы.

Постоянный реестр мест не является первоочередной задачей. При задании профиля/сравнения определить, что именно выбирают и передают в ссылке: группу адреса, конкретный объект или точку. Не использовать хеш текстовой группы как уже гарантированный постоянный ID места и не подменять несколько объектов одним автоматически. Модель сохранения и необходимость внутреннего постоянного ID проектировать под подтверждённый сценарий, без предварительного создания полного реестра.

Первый продукт готов, когда пользователь без входа находит и явно выбирает минимум два места, получает сопоставимые показатели, понимает источники/ограничения и отсутствие данных, может заменить вариант и повторно открыть согласованную ссылку. Проверить desktop/mobile, клавиатуру, прямой URL, ошибки, частичное покрытие и реальные адреса. Технический сценарий реализован и проверен; пользовательскую пользу ещё предстоит проверить с людьми.

Уточнения к этапам:

- Stage 0 готов только при успешных Composer/npm ci/build от пользователя `node`, доступном dev-порту 5173 без `--host`, ответах Laravel `/` и `/up`, миграциях, SQL-проверке PostGIS из Laravel, обычных и GIS-тестах. Shell и `pg_isready` сами по себе готовность не подтверждают.
- Остальные таблицы создавать вместе с функцией: Stage 4–5 — `osm_addresses`, `osm_buildings`, `osm_roads`, `osm_green_areas`, `osm_water`, `osm_railways` и `pg_trgm`; не заранее.
- Крупные дороги: `motorway`, `trunk`, `primary`, `secondary`.
- Спутниковый PoC отдельно согласовать после определения пользовательского вопроса; он не предшествует первому сравнению как обязательный этап. Например, 2016/2021/2025: наличие/число сцен, облачность, маски, NDVI и валидное покрытие. Результат: `year | scenes | valid coverage | median NDVI`. При плохом результате выяснить причины до большого pipeline; успешный ранний PoC не повторять на Stage 14.
- Финальная выборка: центр, окраина, граница покрытия, зелёный район, промзона, рядом с магистралью/железной дорогой, много/мало остановок. Близость к посту воздуха проверять при реализации Stage 11.

### Компоновка и пользовательский путь
