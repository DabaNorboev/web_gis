# Следующие уточнения главной и карты — V1–V3

Статус: план по прямому запросу владельца после [U1–U4](interface-usability-corrections.md). V1 выполнен; V2 и V3 не начаты. Три последовательных чата, каждый на **Sol 6.1 Medium без субагентов**. Новый дизайн-аудит, новые референсы и повтор всей исторической приёмки не требуются.

Главная остаётся единым рабочим экраном. В объёме: удалить лишние кнопки, объединить показ всех целей с их кадрированием, показывать здание при адресном поиске цели как при А/Б, различать совпадающие маршруты. Это уточняет прежние решения о переключателе интерфейсов и запрете неявного fit: показ найденного/выбранного адресного объекта — предусмотренное действие поиска; смена результата или ориентира камерой не управляет.

Основные действующие документы — [структура frontend](../frontend-structure.md), [карта и навигация](../features/home-workspace-map.md), [поездки](../features/trips.md), [проверки](../testing.md). Макет остаётся [визуальным ориентиром](../../experiments/placelens-visual/PlaceLens-visual.html); новые прямые требования владельца имеют приоритет.

## Подтверждённые точки изменений

- `PlaceLayout.vue` выводит InterfaceSwitch, «Сравнить адреса», «Поездки · пилот» и служебную пометку версии. Layout общий, перед его правкой проверить всех потребителей.
- `useInterfacePreference.ts` изначально выбирает classic и читает прежнюю настройку localStorage. Простое удаление кнопок оставит часть пользователей в старой главной без возможности открыть новую — это нужно устранить вместе с удалением переключателя.
- HomePage содержит отдельные «Все цели», «Вместить на карте», «Подробности» и «Сбросить высоту».
- `AddressPicker` для А/Б передаёт `mapState` с найденными группами/подсветкой. `TripPointPicker` цели использует AddressSearch, но не передаёт такое состояние в общую карту; подтверждение отдаёт координату/подпись. Приближение после подтверждения из U1 не заменяет предварительный показ здания.
- `tripMap.ts` рисует маршруты одинаковой шириной 4px с белой обводкой 7px; совпадающие линии могут перекрыть друг друга. Это проблема отображения, а не маршрутного API.

Рабочая база содержит незакоммиченные U1–U3 и свидетельства U4. Перед каждым этапом проверить Git и handoff; сохранить staged/unstaged/untracked. Не начинать параллельные изменения HomePage, Layout и общих picker/map-компонентов. Номера V относятся только к этому документу.

## V1 — убрать лишнее управление

**Чат 1.** Одна небольшая задача по шапке и панели карты, без переписывания поиска/маршрутов.

### Сделать

1. Убрать видимые кнопки «Текущий / Новый», «Сравнить адреса», «Поездки · пилот». Убрать ставшую ненужной пометку предварительной/старой версии. Основная точка входа — бренд/главная; не создавать вместо удалённой навигации ещё одно меню. Не удалять данные или функции самостоятельных поездок: они доступны на главной.
2. Главная `/` всегда открывает актуальное рабочее пространство: при чистом storage, прежнем значении classic, workspace и недоступном storage. Это необходимая часть запроса убрать переключатель. Не оставлять скрытое старое предпочтение, которое определяет доступность новой главной.
3. Удаление кнопок не означает удаления `/compare`, `/trips`, `/address/:id`, их содержимого и прежних переданных ссылок. Не ломать прямое открытие этих путей, не добавлять редиректы/новый router. Старую реализацию не вычищать большим рефакторингом ради скрытия кнопки.
4. Убрать видимую кнопку сброса высоты карты. Ручка регулировки, выбранная пользователем высота, раскрытие/возврат и сворачивание панели остаются. Сброс ширин таблицы в этот запрос не входит.
5. Убрать отдельную кнопку «Подробности» из панели карты. Подробности по клику на цель/свою сторону и ⓘ в таблице сохраняются; причины, повтор и выбор уличных точек остаются доступны. Не трактовать запрос как удаление всех ⓘ/источников.
6. Вместо двух «Все цели» и «Вместить на карте» оставить одну **«Все цели»**: явное нажатие включает показ всех имеющихся целей и кадрирует их вместе с доступными выбранными А/Б. Сначала обновить показ, затем получить актуальные границы. Кнопка не рассчитывает новые маршруты и не меняет URL. «Одна цель» не удаляется автоматически, если продолжает выполнять отдельное действие.
7. Раннее нажатие до готовности карты корректно ждёт ready; последующее изменение сценария/целей отменяет устаревшее намерение. Удалённая цель не включается в границы. Пустая карта не получает выдуманные bounds. Изменение ориентира/resize само по себе по-прежнему не вызывает fit.

**Файлы:** PlaceLayout/useInterfacePreference, HomePage, изолированные стили и затронутые тесты. Перед изменением общих props/emits проверить потребителей и сообщить, какие общие компоненты затрагиваются.

**Готово:** чистый и прежний classic-браузер попадают в рабочую главную без переключателя. Шапка и панель карты заметно короче. Одно нажатие «Все цели» из режима одной цели показывает и вмещает актуальные объекты; детали доступны через цель/ⓘ. Высота, ввод, результаты и камера при обычном resize сохраняются.

**Проверки:** typecheck, целевые preference/home-layout/map tests, browser чистого/старого/отказавшего storage, прямых прежних путей, одной кнопки all+fit и доступности деталей. 1440×900 и 390×844. Устаревшие тесты переключения версии заменить проверками нового согласованного поведения, не удаляя независимые проверки владельцев/истории/приватности.

## V2 — здание цели при адресном поиске

**Чат 2. Зависимость: V1.** Главное исправление: адрес цели должен иметь тот же пространственный предпросмотр, что А/Б.

### Сделать

- Для активной редактируемой цели передавать в общую карту найденные адресные группы, здания/объекты и подсветку из выдачи, используя существующие search/choice/map contracts. Поиск, выбор группы, переход стрелками, фокус объекта и подтверждение согласованы между списком и картой.
- Выбираемое здание должно реально выделяться/показываться, а не только вызывать перелёт камеры к координате. Применять существующую геометрию/маркеры адресного набора, как у А/Б. Не рисовать выдуманный контур при отсутствии геометрии.
- Выбор конкретного объекта через список/карту подтверждает адрес цели, показывает «Адрес выбран» и фокусирует правильное место. Текстовая группа из нескольких корпусов не считается подтверждённым объектом. Подсветка не меняет координаты цели до явного выбора.
- Состояние предпросмотра относится к сценарию, стабильному ID цели и текущему поиску. Только одна активная цель управляет preview. Переключение редактора, очистка поиска, удаление цели и закрытие/сохранение карточки корректно убирают временную подсветку; поздний ответ другого поиска её не возвращает и не двигает камеру.
- Предпросмотр не запускает поездки, не инвалидирует прежние результаты до подтверждения новой геометрии, не меняет А/Б или личные ориентиры. Подтверждение новой точки действует по существующим правилам независимости.
- Показывать preview в том же MapLibre с приоритетом адресного выбора, затем возвращать обычный обзор. Click-dispatch не должен одним нажатием выбирать здание и одновременно другую маршрутную цель/улицу.
- На телефоне поле остаётся редактируемым; не уводить в другой экран при каждом вводе символа. При явном переходе на карту видно актуальный preview, возврат сохраняет введённое. Выбор карты/улицы и самостоятельный старт не получают чужую адресную подсветку.
- Не ломать прежний выбор А/Б и самостоятельные поездки. Если переиспользуется общий TripPointPicker/AddressPicker, публичные контракты расширять совместимо, без второго loader или встроенной карты внутри поля.

**Файлы:** TripPointPicker, AddressSearch/AddressPicker/useAddressChoice по необходимости; HomeTripsEditor/Panel, HomePage, HomeWorkspaceMap и типы preview. Сначала проследить существующий путь А/Б, затем добавить недостающее соединение для целей. Не создавать параллельный поиск и GIS в UI.

**Готово:** ввести неоднозначный адрес цели, увидеть те же объекты/номера на карте, подсветить стрелками конкретный корпус, явно подтвердить и получить правильную цель. Изменение другой цели/запоздалый ответ не возвращает старое здание. А/Б продолжают работать как раньше.

**Проверки:** typecheck; целевые frontend state/preview и browser поиск → несколько объектов → подсветка → подтверждение в обе стороны, удаление/переключение цели во время запроса. Проверить геометрию/выделение реального source, не только совпадение центра. Использовать синтетический адрес с различимыми объектами, как в прежних tests; не искать случайную подходящую выдачу вместо воспроизводимого сценария. 1440×900/390×844, без лишних расчётных POST.

## V3 — различимые совпадающие маршруты и короткая приёмка

**Чат 3. Зависимость: V2.** Устранить перекрытие линий, не меняя рассчитанные пути, затем проверить V1–V3 вместе. Отдельный четвёртый чат для той же проверки не нужен.

### Сделать

- Выбрать простой способ разведения отрисовки совпадающих маршрутов: экранные смещения, сочетание обводки/ширины/штриховки и явного выбранного пути. Проверить способ на реально совпадающих линиях; смены opacity или порядка слоёв недостаточно, если нижний путь исчезает.
- А и Б остаются различимы на общем участке. При нескольких целях одной стороны сохраняется понятная принадлежность пути к цели через выбор/подсветку и подписи. Не обещать различимость только на концах, когда общий участок скрыт целиком.
- Сохранить возможность выбрать нужную сторону/цель через маркер/подробности, даже если геометрии полностью совпадают. Результат клика по совпавшим линиям не должен молча выбирать чужую ячейку; нужен определённый приоритет с доступным переходом к альтернативе.
- Использовать стабильную идентичность сценария/стороны/цели; не request-local index. Противоположное направление одинаковой линии, zoom, выбранный/невыбранный режим и обе стороны должны быть проверены.
- Разведение линий — только визуализация. Исходные координаты GeoJSON, метры, секунды, диагностические токены и bounds расчётной геометрии не менять. Смещение экранной линии не означает реальный параллельный путь. Не добавлять GIS-анализ пересечений, новый routing API или библиотеку ради стиля.
- Не создавать неподтверждённые подходы, соединители и линии для отказов. При смене режима/адреса старая линия не сохраняется. Тема, повтор подложки, размер карты и обновление ориентира сохраняют актуальную геометрию без лишних запросов/fit.

**Файлы:** homeMap/tripMap/tripOverlay, CityMap и prepared properties по необходимости. Изменения общего renderer проверять на прежних картах; defaults старых потребителей сохраняются.

**Готово:** на полностью и частично совпадающих путях А/Б видно, что присутствуют обе стороны; выбор каждой показывает свои подробности и её связь с целью. На трёх целях общие участки не уничтожают доступ к другим результатам. Ручная регулировка и выбор здания цели из V2 работают.

**Проверки:** frontend renderer/map tokens и целевые browser fixtures полного/частичного совпадения, обратного направления, выбора каждой стороны/цели, theme/reload. Просмотреть 1440×900 и 390×844 на двух zoom; 320×740 — доступность управления.

После исправления коротко пройти V1–V3: чистый/старый storage → главная без лишней шапки → адрес цели с предпросмотром → расчёт пары с совпадающими маршрутами → одна цель → «Все цели» с fit → детали своей стороны. Проверить сохранность результатов/ориентиров и количества POST, прежние direct URLs. Не повторять весь старый suite без риска общей регрессии. В итог включить воспроизводимые дефекты либо технический вердикт в проверенных границах; визуальную оценку делает владелец.

## Организация, проверки и передача

Порядок: **V1 → V2 → V3**, один исполнитель за раз, Sol 6.1 Medium без субагентов и повышения усилия. Новые подсистемы не проектировать, старую реализацию не чистить попутно. Использовать актуальный макет и рабочие компоненты.

Никаких изменений .env, volumes, GIS/БД, API, guards, исходных данных, лимитов, зависимостей и production assets. Node-команды — в Compose `node` пользователем `node`; выбор проверок и побочные эффекты — [testing](../testing.md). Новые тесты только на содержательные изменения и найденные риски, существующие fixtures переиспользовать. Не выдавать старые отчёты за новые прогоны. Синтетические API и настоящий MapLibre не подтверждают рабочие GIS/маршрутизаторы или физический телефон.

После каждого этапа обновить основной текущий контракт/changelog по фактическому поведению и оставить здесь короткий handoff: изменённые границы, проверки, 1–3 снимка, оставшиеся вопросы. Снимки должны показывать видимый результат, в V2 — здание/объекты, в V3 — совпадающие маршруты, а не только пустой экран. Не утверждать визуальный успех только по зелёным assertions.

После docs-правок запускать `scripts/check-docs` без исключений и `git diff --check`; прежние замечания отделять от новых. Старую историю и большой план не удалять ради размера; этот документ держать до 40 KiB. Коммиты и push — только по отдельному поручению.
