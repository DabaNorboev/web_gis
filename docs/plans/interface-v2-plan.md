# Второй интерфейс PlaceLens

Статус: **G3.5 — независимая функциональная приёмка завершена 27.10.2026 в проверенных границах; G35-F1 закрыт после независимой перепроверки текущей сборки. Можно начинать G4.** G2–G3.4 находятся в общем незакоммиченном дереве. G4 и общая визуальная доводка не начаты. Ограничения синтетического стенда, устройств и реальных GIS/маршрутизаторов сохранены в разделе G3.5. Ниже сохранена история предыдущих этапов; текущий контракт — [trips](../features/trips.md#единое-пространство-на-главной). Метка verified относится к выполненной приёмке, а не к будущим этапам плана.

Самостоятельные макеты и обсуждение описаны в [выжимке диалога](../history/interface-prototypes-2026-10-27.md). [UX-решения](interface-prototype-ux.md) реализованы в экспериментальном макете 28–29.10.2026, но в приложение не перенесены. Порядок дальнейшей работы и границы переноса имеют основное место в [плане интеграции G4](interface-integration.md). G4 не начат; результаты макета не заменяют приёмку приложения.

**Изменение порядка после G2:** владелец предложил сначала собрать весь существующий функционал на главной, затем продолжать оформление. Следующий G3 — функциональная интеграция единого рабочего пространства. Прежний порядок «отдельно переоформить профиль/сравнение, потом поездки» заменён. Выполненный G2 сохраняется как техническая основа; общий визуальный редизайн ещё не завершён.

## Цель и границы

Создать второй, понятный и последовательный интерфейс существующего продукта. Сохранить текущий интерфейс и дать возможность переключаться между двумя представлениями. Пользователь должен без устного объяснения понимать, с чего начать, что выбрано, что можно сделать дальше и где результат.

Владелец сообщил, что при знакомстве с проектом его другу потребовались объяснения. Это основание проверить понятность; точные места затруднений пока не установлены. Рекомендации прошлого чата основаны на статичных скриншотах без проверки мобильного поведения, поэтому визуальные диагнозы требуют сверки с приложением.

Будущий сценарий владельца: важные места и условия → приблизительная территория поиска → ручное добавление объявлений → отдельная проверка вариантов → список результатов → сравнение пары → вопросы для самостоятельной проверки. В этом задании он служит ориентиром расширения интерфейса. Пересмотр продуктового видения будет документироваться отдельно; этот план не заменяет [product](../product.md) и [project-vision](project-vision.md).

В объём всего плана входят расположение блоков, подписи, визуальная иерархия, навигация между существующими действиями, представление результатов, оформление карты и адаптивность. Переключатель интерфейсов — единственная новая пользовательская возможность последующих этапов. В G1 выполняются только аудит и обособленный макет; переключатель не реализуется. Изменения способа взаимодействия допустимы в пределах существующих операций, без новых вычислений и обещаний.

За рамками:

- Объявления, бюджет, цена/площадь, хранение вариантов и аккаунты.
- Область поиска, временные пороги, итоговые статусы соответствия условиям.
- Сравнение более двух вариантов, увеличение лимита личных мест, отдельные режимы для каждого места.
- Новый общий объект «Место» в API/БД, новые источники, изменение маршрутизации, guards или геоаналитики.
- Унификация произвольной точки и адресного профиля: точке доступен существующий анализ остановок, адресному объекту — существующий профиль.
- Публикация и замена текущего интерфейса по умолчанию. Решение о дальнейшем использовании принимается после проверки второй версии.

| Рекомендация | Решение для этого плана |
|---|---|
| Единое рабочее пространство | Общий каркас и правила взаимодействия; на макете проверить размещение ввода слева, карты рядом и результатов ниже. Единый экран для всех сценариев пока не предрешён |
| Кандидаты и важные места в списке | Для сравнения показывать существующие А/Б, для поездок — существующий старт и до трёх целей. Не изображать общий сохранённый набор между страницами, которого нет |

| Общие шкалы и полоски | Вторичный способ чтения после проверки макета. Только сопоставимые числа; null, отсутствие маршрута и объект за радиусом не превращаются в нулевую или обрезанную полоску. Близость не окрашивается как безусловное преимущество |
| Меньше крупных заголовков и пустого места | Короткая подсказка в пустом состоянии; после выбора — предметный заголовок, выбор и следующее действие |
| Поездки без отдельной вкладки | Проверить в новом сравнении секции «Поездки» / «Окружение» / «Данные» в общей области результата. Самостоятельные поездки и доступ к ним сохраняются |
| Пешком/авто сегментным переключателем | Использовать существующий общий режим сценария; сохранить текущую инвалидацию результатов и уличных точек при изменении режима |
| Активное поле вместо вкладок над картой | У активного места явно включается «Выбрать на карте», карта показывает, что именно выбирается. Обычный фокус ввода не должен неожиданно включать выбор координаты |
| Скрыть технические сведения | Подробности собрать в доступные раскрываемые блоки; ограничения, меняющие смысл результата, оставить рядом с ним |
| Спокойная карта, один активный радиус | Приглушить декоративную подложку. Вариант с одним кругом проверить на макете; в сравнении обе стороны должны сохранять понятный одинаковый радиус анализа |
| Убрать выбор центра карты | Сохранить доступную клавиатурную альтернативу клику. Можно изменить расположение и подпись, но не убрать возможность выбора без мыши |
| Связь строк с картой наведением | Низкий приоритет. Сначала явное нажатие и работа с клавиатурой; наведение позднее как дополнительная подсветка, без самовольного перемещения камеры |
| Мобильная нижняя шторка | Проверить на макете, включая короткий экран и открытую клавиатуру. Предусмотреть явные кнопки раскрытия/сворачивания; жест не единственный способ управления |

## Предлагаемое устройство второго интерфейса

Общие элементы: компактная шапка, навигация по существующим задачам, переключатель интерфейса, единые поля и действия, карта, узнаваемая область результата и блоки сведений. В новом интерфейсе не показывать пока неработающие пункты «Область поиска», «Объявления», «Бюджет».

Первоначальная desktop-схема до уточнения владельцем; актуальное направление — в разделе G1.1 ниже:

```text
PlaceLens · Красноярск     Поиск | Сравнение | Поездки     Интерфейс
┌────────────────────┬──────────────────────────────────────────┐
│ Выбранные объекты  │ Карта                                    │
│ и ввод            │ Слои, тема, выбранный объект/маршрут      │
│ Основное действие │                                          │
├────────────────────┴──────────────────────────────────────────┤
│ Результаты: краткие факты / поездки / окружение / данные       │
└───────────────────────────────────────────────────────────────┘
```

Это кандидат на компоновку, а не требование всегда держать три панели одновременно. На коротком экране результат должен оставаться читаемым, карта — пригодной для выбора. Предпочтительный вариант определяется макетом, без постоянного увеличения числа вложенных прокруток.

Правила по сценариям:

- **Поиск и точка.** Один заметный вход в поиск, короткий пример, явное различие адресного объекта и координаты. При выборе точки — существующие остановки и подпись точки. После подтверждения адресного объекта — профиль.
- **Профиль.** Вверху выбранный объект, радиус и действие сравнения. Затем компактные факты и подробности. Парки, растительность, вода, дороги, пути и остановки доступны без потери источников и причин неизвестности.
- **Сравнение.** А/Б всегда узнаваемы; замена каждого варианта независима. Общий радиус, краткие различия и строки значений. Область результата шире нынешней узкой панели. Проверить одну общую карту и существующие две карты на одном сценарии; выбрать до реализации сравнения. При общей карте явный выбор стороны и маршрута обязателен.
- **Поездки.** Старт, цели, общий режим и запуск расчёта находятся в предсказуемых местах. Результат связан с соответствующей целью. Уточнение улиц, повтор и независимые ошибки сохраняются. Уличные точки не подменяют исходные объекты.
- **Телефон.** Сохраняются выбранное место и понятное переключение «Результаты / Карта». Проверить нижнюю панель для краткого результата; длинные сведения доступны для нормального чтения. При смене компоновки ввод и выбор не сбрасываются.

Оформление ограничений:

- Рядом со значением — короткая, содержательная подпись: «по прямой», «без пробок», «уличная часть», «подходы неизвестны», «нет данных», «дата наблюдения неизвестна».
- Рядом с отказом — причина и доступное следующее действие. Причина, требующая выбора улицы, не скрывается в «Технических сведениях».
- В подробностях — источники, снимки, даты, метод, покрытие и остальные ограничения. Дата публикации/импорта не подменяет дату наблюдения.
- Числа, ошибки, ожидание и отсутствие данных различаются текстом, а не только цветом. Декоративная компактность не удаляет значимые сведения.

### Наблюдения и гипотезы о понятности

Это экспертный проход одного исполнителя, а не usability-тест с новым человеком. Наблюдаемые действия отделены от предполагаемых причин затруднений.

| Вопрос | Наблюдение в текущем UI / коде | Предположение и решение в макете |
|---|---|---|
| С чего начать | Главная показывает адресный поиск и объясняет путь к сравнению. На desktop есть подсказка о клике карты; на телефоне карта расположена ниже вводного текста | Альтернатива «адрес / точка» может восприниматься как два равнозначных способа получить профиль. В макете это два подписанных действия с разными результатами |
| Что выбрано | Поиск «Мира, 10» предложил проспект Мира и улицу Мира; явное нажатие выбранного адреса с одним объектом открыло профиль. Для нескольких объектов `AddressPicker` отдельно требует выбора объекта; это дополнительно проверено по коду, не по реальной многозначной группе | Сохранить явность, но первым показывать тип объекта и краткое объяснение. В макете один адрес намеренно имеет здание и отдельную адресную точку |
| Точка или объект | «Анализировать центр карты» дал остановки и адресную подпись контура. Координаты оставались исходными; UI предупреждал, что подпись не переносит точку | Крупный адресный заголовок внутри результата точки может скрыть различие. В макете основной заголовок «Остановки рядом», выбранное — «Произвольная точка», переход к адресному поиску явный |

### Предлагаемая компоновка и небольшая альтернатива

**Рекомендуется: результаты рядом с одной общей картой на desktop; на телефоне — отдельные представления «Результаты / Карта».** Это предложение на оценку, не утверждённый дизайн.

Desktop: компактная шапка с тремя сценариями

│ Выбор → действие → факты     │ Одна карта                  │

└─────────────────────────────┴─────────────────────────────┘

### Проверки G1 и исправления макета

В браузере пройдены поиск, явный выбор объекта клавиатурой, профиль → А/Б, раздельная замена сторон, источники и дата «неизвестна», радиус, отдельный выбор точки/остановки, самостоятельные и сравнительные поездки обоих режимов. В сравнении проверены автомобильное уточнение Б и отдельный пересчёт; пешие улицы старта/цели выбираются явно, А может дать результат при ещё не уточнённом Б. Смена режима очищает прежние результаты и улицы. Макет не заменяет реальные проверки guards.

Размеры макета: 1440×900, 390×844, 1280×560; дополнительно проверены ввод и подтверждение точки на 390×480 (модель уменьшенной доступной высоты). Проверены обычная прокрутка, видимость кнопок карты, отсутствие горизонтального переполнения, сохранение выбора при переключении «Карта / Результаты», Enter и стрелки для выбора на схеме. Физическая телефонная клавиатура, реальный touch и screen reader этим не подтверждены.

Исправлены обнаруженные в макете проблемы: нижняя панель карты выходила за первый экран; после выбора объекта сохранялся неудачный скролл; автомобильный пересчёт ошибочно ожидал две уличные точки; возврат из уточнения отправлял к началу формы; подписи сторон были неоднозначными; реальная выбранная уличная точка не использовалась для начала/конца иллюстративной линии. Контролы и ограничения теперь остаются доступны. После явного расчёта/уточнения фокус переходит к соответствующей карточке результата.

Синтаксис `app.js` проверен `docker compose exec --user node node node --check experiments/interface-v2/app.js`. HTTP preview возвращает 200. Рабочие TS/Vue, PHP и GIS не менялись, поэтому их suites и production build не запускались. Локальные ссылки, отсутствие внешних зависимостей и изоляция от app entry graph проверены при завершении G1.

### Что оценить владельцу перед G2

1. Подходит ли порядок «выбор → заметное действие → компактные факты», понятны ли разные результаты адреса и точки.
2. Достаточно ли ширины результатов рядом с картой и читаемы ли строки А/Б.
3. Приемлема ли одна общая карта с явным выбором стороны/маршрута; дальние адреса потребуют реальной проверки.
4. Подходит ли мобильное переключение вместо длинной нижней шторки.
5. Ясны ли необходимость уточнения улиц и то, что успех уличной части не даёт полного пути от объектов.

G2 остаётся отдельным заданием после просмотра. Его первый срез: предпочтение «Текущий / Новый», один владелец состояния, реальный поиск/точка в новом каркасе. Не переносить макетный state или hash-навигацию в production. Сохранить действующие API, null/coverage/историю, текущий интерфейс и проверки поздних ответов. Ошибку шапки включить в явный объём G2 либо отдельного исправления с регрессией обеих навигационных ссылок. Новые статусы, данные, объявления и подбор области не добавлять.

## G1.1: уточнённый визуальный ориентир владельца

Исходный статус 27.10.2026, до разрешения реализации: предложен новый автономный HTML-прототип рабочего пространства, версия «(2)». Рабочие страницы тогда не менялись; G2 не был начат. Выполнены разбор исходника и затем просмотр двух desktop-скриншотов, присланных владельцем. Самостоятельной браузерной проверки этого HTML не было: открытие `file://` встроенным браузером заблокировано, обход ограничения не выполнялся. Заявленный автором прогон jsdom самостоятельно не повторялся.

Владелец предпочитает направление «список слева → общая карта → матрица под картой», с выбором кандидата из списка/столбца/маркера и цели из списка/строки. На телефоне предложена раскрываемая панель результата выбранного кандидата. Это новый кандидат на компоновку вместо боковой колонки результатов, рекомендованной первым G1; прежний раздел G1 сохраняется как история проверки. Окончательное визуальное согласование и проверка короткого экрана ещё не выполнены.

В прототипе разделены обсуждаемый целевой образ и представление на текущих возможностях. Эти демонстрационные режимы не подменяют будущий переключатель рабочего приложения «Текущий / Новый».

Подтверждено по текущим контрактам и исходнику нового макета:

- Существующие возможности: А/Б, до трёх общих целей внутри сравнения, общий режим walking/driving, остановки по произвольной точке. Общего набора целей между всеми страницами нет.
- Только целевой образ: третий кандидат, индивидуальные режимы/временные пороги, проверка соответствия и новые операции с произвольной точкой. Это темы будущих решений, а не разрешённый backlog G2.
- Новая версия макета показывает оба режима и общие цели, заменяет «Барьеры» нейтральным названием дорог/путей и явно предупреждает о синтетических данных. Вымышленные минуты подтверждают только плотность содержимого, не результат маршрутизатора.

До перехода к реализации проверить/доработать:

1. Высота: `min-height: 560px` остаётся и у desktop, и у мобильной рамки, поэтому ограничение `100dvh - 84px` не гарантирует размещение на коротком экране. Высота внешнего баннера меняется при переносе текста/кнопок. Нужна проверка всей страницы, а не только заданной высоты приложения.
2. Шторка: до 330 px приходится только на тело; ручка, А/Б, общий режим и отступы добавляют высоту. Проверить раскрытие, доступ к последней строке и сохранение пригодной карты; предусмотреть явное действие полного открытия результатов.
3. Пешая карта: сейчас условная линия начинается в маркере кандидата и заканчивается в маркере цели. Для представления текущих возможностей нужны отдельные исходные объекты и выбранные уличные точки, линия только между улицами, без неподтверждённых соединителей.
4. Шкалы: время ограничивается 60 минутами, расстояния — 600 м, поэтому большие разные значения могут выглядеть одинаковыми. До переноса выбрать общую шкалу или явный признак выхода за неё. Штриховка «за радиусом» и наличие геометрии/слоя должны иметь раздельные причины.
5. Состояния: дополнить выбранный каркас пустым вводом, поиском/подтверждением объекта, загрузкой, независимым отказом А/Б и уточнением улиц. Первый макет G1 уже содержит полезные примеры этих действий; не заменять их одним заполненным демонстрационным экраном.

### Уточнение по двум скриншотам владельца

Владелец показал desktop в целевом образе и в варианте текущих возможностей и предложил растянуть рабочую область на всю ширину. Это принято как требование к следующему макету и новому каркасу; остальные детали дизайна не считаются автоматически согласованными.

На изображениях видны крупные внешние поля и свободное место под ограниченной по высоте рамкой. Основное пространство нового интерфейса занимает доступную ширину и высоту под шапкой, с небольшими краевыми отступами. Ограничения `max-width: 1220px` и максимальная высота 780 px из демонстрационной рамки в рабочий desktop-каркас не переносятся.

```text
Компактная шапка на всю ширину
┌──────────────────┬─────────────────────────────────────────────┐
│ Поиск, А/Б       │ Одна карта                                  │
│ и цели           │                                             │
│                  ├─────────────────────────────────────────────┤
│                  │ Результаты: поездки / окружение              │
└──────────────────┴─────────────────────────────────────────────┘
```

- Левый список остаётся компактной колонкой ориентировочно 280–320 px на широком экране. Дополнительная ширина достаётся карте и матрице, а не растянутому тексту карточек.
- Матрица находится под картой справа от списка. Соотношение высот можно менять; нужны явные действия развернуть/свернуть результаты, доступные без перетаскивания. Заголовки А/Б и показателей сохраняют контекст при прокрутке таблицы.
- На скриншотах верхние маркеры целей частично обрезаны, а контролы занимают тот же участок. В следующем макете учитывать место под контролы и поля камеры. Простое увеличение ширины SVG с `preserveAspectRatio="slice"` не решает обрезку; в рабочей MapLibre проверять отступы камеры и resize, без автоматического fitBounds при каждом изменении панелей.
- Разделы поездок и окружения сохраняются внутри одной матрицы; отдельные вкладки не требуются для показанного объёма. Режим расчёта размещать рядом с целями либо в постоянной панели над результатами, чтобы смена режима не требовала поиска внутри прокрутки.
- На текущем скриншоте окружение находится ниже первого видимого набора поездок. Увеличение доступной высоты и раскрытие результатов должны дать возможность прочитать его без уменьшения всего интерфейса.
- Проверены только присланные desktop-изображения. Короткий экран, мобильная шторка, действия, реальная камера и сохранение состояния по этим изображениям не подтверждаются. Снимки в темной теме не означают отдельного согласования глобальной темы приложения.

## Переключение интерфейсов

Предлагаемые обозначения: **«Текущий» / «Новый»**; до окончания проверки второй отмечен как предварительный. Переключатель доступен в общей шапке всех четырёх страниц и показывает активное значение.

Контракт:

1. Те же маршруты: `/`, `/address/:id`, `/compare`, `/trips`. Новый интерфейс не требует отдельной копии backend routes или новых форматов ссылок.
2. По умолчанию остаётся текущий интерфейс. Явный выбор сохраняется в `localStorage` отдельным ключом со значением только версии интерфейса. Координаты, подписи личных мест и результаты туда не добавляются.
3. Если storage недоступен или значение неизвестно, приложение работает с текущим интерфейсом. Явное переключение продолжает работать в памяти открытой страницы; предпочтение на следующую загрузку в этом случае не гарантируется.
4. В пределах страницы переключение происходит без reload, очистки формы или запуска нового расчёта. Сохраняются выбранные объекты, радиус, режим, цели, уличные точки, результаты, ошибки, черновики и актуальные запросы. Раскрытия и прокрутка могут иметь собственное состояние представления.
5. Переключение не меняет query/fragment, не добавляет запись в историю анализа и не превращает обычную ссылку в личную. Получатель ссылки открывает данные в своём выбранном интерфейсе.
6. При переходе между страницами остаются нынешние правила переноса состояния через ссылки. Переключатель не обещает новое глобальное сохранение всех черновиков между сценариями.
7. Выбранный интерфейс определяется до монтирования страницы; второе представление загружается по необходимости. Не монтировать одновременно две рабочие формы и два комплекта карт ради быстрого переключения.
8. После переключения фокус остаётся на доступном управлении либо переносится к заголовку соответствующего раздела. Поздний ответ не вызывает неожиданного скролла или возврата к старому представлению.
9. Камера и слои карты по возможности сохраняются при смене компоновки. При вынужденном пересоздании восстанавливается отображение, но не повторяется аналитический запрос или прежняя команда fitBounds.

## Технический подход

Сейчас `resources/js/app.js` выбирает страницу по pathname. Состояние и эффекты находятся в страницах/composables; часть черновиков и DOM-поведения принадлежит дочерним компонентам. Простая замена корневого компонента на `NewComparePage` потеряет часть состояния и может повторить запросы. Полное копирование страниц создаст два расходящихся сценария.

Предлагается:

- Добавить небольшой модуль предпочтения интерфейса и общий переключатель. Сохранять существующий выбор страницы по pathname; отдельные Vue Router и глобальное хранилище ради этой работы не нужны.
- Для каждого сценария оставлять одного постоянно смонтированного владельца состояния и URL/history. Менять представление вокруг него. Если нужен перенос из страницы в composable, делать его локально, при подключении соответствующего экрана, с проверкой прежнего поведения.
- Повторно использовать существующие API-модули, composables расчёта, типы, форматирование и guards. Существующие виджеты выбора и карт сохранять с устойчивой идентичностью там, где возможно. Вынести только тот локальный черновик, который иначе теряется при переключении.
- Новые layouts и компоненты представления размещать обособленно, с собственным корневым классом/стилями. Не переопределять глобальные стили так, чтобы текущий интерфейс менялся вслед за новым.
- DOM-эффекты страницы привязывать к актуальному представлению через refs и конкретные действия. Не держать скрытую старую страницу, дублирующиеся ID, listeners и карты.
- Работу с картой отделять от компоновки. При переносе проверять resize, выбранную сторону, слои и overlay; не менять правила координат/геометрии ради внешнего вида.
- Не вводить общий универсальный «движок рабочего пространства» или новую предметную модель ради двух представлений. Переносить только необходимую ответственность.

Пути новых компонентов и точная граница постоянной карты уточняются после макетов и первого вертикального среза. Это не основание заранее реорганизовать весь frontend.

### 3. Собрать существующие возможности на главной

Пересмотрено 27.10.2026 по прямому указанию владельца после просмотра G2. Сначала рабочая связность сценария, затем доводка оформления по референсу. Это перенос существующих операций в единое пространство нового интерфейса, без расширения аналитики.

Пользовательский проход, который должен работать без переходов между отдельными рабочими страницами:

1. Найти и явно подтвердить адресный объект; увидеть его профиль на главной.
2. Добавить второй адрес в существующие слоты А/Б; получить сравнение с общим радиусом, независимо заменить или убрать сторону. При одном выбранном объекте показывается его профиль.
3. Задать до трёх общих целей, выбрать общий режим пешком/авто и рассчитать поездки от выбранных адресов. Одного адреса достаточно для проверки его поездок; второго — для сопоставления.
4. Уточнить дорожную/уличную точку, повторить отдельный расчёт, прочитать независимый отказ и неизвестные подходы, показать нужный маршрут на карте.
5. Сохранить самостоятельный сценарий от произвольного старта к 1–3 целям как доступное действие в том же пространстве. Произвольный старт не становится адресным кандидатом; различия с общими целями сравнения остаются явными. Не объединять черновики автоматически и не обещать общее постоянное хранилище.
6. Сохранить анализ остановок по произвольной точке, слои, темы интересов, источники/методы/даты, обычные и личные ссылки и историю.

Работу выполнять последовательными рабочими срезами: объект/профиль → А/Б → цели и оба режима поездок → самостоятельный старт, карта и ссылки → проверка полного прохода. Внешний вид на этом этапе использует простые существующие компоненты. Не требуется ещё один синтетический макет или предварительная полировка всех карточек.

Технические границы:

- У пространства один владелец выбранных объектов, радиуса, активного контекста и согласования URL. Использовать существующие API/composables; один профиль не запрашивать отдельно для карточки и сравнения. Состояние расчёта не переносить в MapLibre или UI-форматтеры.
- Не монтировать четыре прежние страницы целиком внутри главной и не прятать их CSS: это даст несколько шапок, карт, observers и конфликтующих записей history. Переносить существующую ответственность небольшими проверяемыми частями, не копировать контроллеры состояния.
- Карта обслуживает явный текущий контекст: объект/остановки/выбранная поездка/выбор улицы. Смена отображаемого слоя или результата не запускает расчёт; исходные объекты и уличные точки различаются.
- URL и личные ссылки требуют единого адаптера пространства: существующие `/address/:id`, `/compare` и `/trips` продолжают открываться и восстанавливаться. Новый путь пользователя выполняется на главной; старые страницы текущего интерфейса остаются доступны. До кода адаптера явно установить, как представлены одиночный объект, пара и самостоятельный старт; личные координаты не переносить в query и не менять версионную проверку fragment.
- Переключатель представления сохраняет выбранное и черновики. Если часть единого пространства отсутствует в текущем интерфейсе главной, её состояние остаётся у общего владельца, а не уничтожается при переключении. Не сохранять личные данные в localStorage ради обхода размонтирования.
- Работа с текстом/действиями и минимальная доступность входят в каждый срез. Пороги, третий кандидат, объявления и область поиска в G3 не включаются.

**Готово:** основной проход «выбрал А → увидел профиль → добавил Б → задал цели → проверил поездки → уточнил улицу/отказ → заменил вариант» выполняется на главной без повторного ввода и ручного переноса координат. Самостоятельный старт, точка/остановки и прежние прямые ссылки не потеряны. Поздние ответы, независимость результатов, null, приватность и история проверены. Только наличие вкладок или ссылок на старые страницы этот критерий не выполняет.

### 5. Согласовать карту и адаптивность

Приглушить декоративную подложку, выровнять карточки выбора, управление слоями, единицы и пояснения. Завершить мобильную и короткую компоновки всех экранов, убрать конфликтующие прокрутки. Изменения стиля аналитических слоёв не должны менять состав данных.

**Готово:** выбранное место и результат узнаваемы на всех размерах; основные действия не закрываются панелью или клавиатурой; текущий интерфейс визуально сохранён. Дополнительное наведение на строки делать только после основного объёма, если оно ещё нужно.

### 6. Проверить понятность и стабильность

Дать знакомому и, по возможности, человеку без опыта проекта задания без предварительного объяснения: найти адрес, сравнить со вторым, задать поездку, понять отказ/неизвестность, вернуться к результату и переключить интерфейс. Смотреть на первую попытку, ошибки, поиск следующего действия и необходимость подсказок; небольшую проверку не объявлять подтверждением всей продуктовой пользы.

Исправить обнаруженные препятствия, повторить затронутые сценарии. Обновить текущие документы frontend/функций только там, где изменилось поведение представления. Отметить выполненные этапы и нерешённые ограничения здесь.

**Готово:** основные задания выполняются без устного объяснения владельца, неизвестность результата понимается правильно, критичных ошибок и потери состояния нет. Решение о default и судьбе текущего вида — отдельное; старая версия автоматически не удаляется.

## Проверки реализации

Порядок и эффекты команд — в [testing](../testing.md); существующие регрессии сохраняются. Node-команды выполнять в Compose-сервисе `node` от пользователя `node`. Build — в новый временный каталог или через существующий browser-стенд, без перезаписи опубликованных assets как побочного эффекта.

| Граница | Что проверить |
|---|---|
| Переключатель | Default, явный выбор, reload, переходы страниц, отказ storage, неизвестное значение, одинаковые URL/fragment до и после переключения |
| Состояние | Переключение с незавершённым вводом, результатом, ошибкой, расчётом в процессе, выбранными уличными точками. Нет двух запросов/listeners и записи старого ответа |
| Ссылки и история | Прямое открытие четырёх маршрутов; обычные и личные ссылки; Back/Forward; переключение не создаёт историю анализа и не раскрывает личные точки |
| Карта | Тема/слои, выбранный объект и маршрут, resize, отказ подложки, повтор, независимые А/Б, явное подтверждение объекта/улицы |
| Представление | Пусто/loading/успех/частичный отказ/неизвестность; null не становится нулём; источники доступны; ограничения не пропадают при уплотнении |
| Размеры и ввод | Существующая матрица Playwright, desktop/mobile/короткий экран, клавиатура и фокус; дополнительно ручная проверка открытой мобильной клавиатуры |
| Текущий интерфейс | Те же основные сценарии и сопоставимые снимки компоновки до/после. Новые стили и перенос state не меняют прежний вид и контракты |

Для UI/TS: typecheck, относящиеся frontend-тесты и browser-сценарии; общие изменения требуют проверки обеих версий. Не писать отдельные тесты на каждое декоративное свойство. PHP/GIS-прогоны не требуются только из-за смены компоновки, если соответствующие границы не менялись. Синтетические browser-тесты не подтверждают пригодность реальных пеших путей.
