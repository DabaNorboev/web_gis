# Исправление интерфейса после оценки владельцем

Статус: план, реализация не начата. Владелец 31.10.2026 не принял интерфейс: нет единой стилистики, редактор целей непонятен, много текста, карта мала, панели и колонки нельзя настроить. Техническая G4.6 из [плана интеграции](interface-integration.md) остаётся свидетельством функциональных проверок, но не означает принятия UX. Этот документ — основное место следующего объёма исправлений.

**Все ведущие — Sol 6.1 Medium, без повышения модели/усилия. По умолчанию без субагентов. Четыре последовательных чата; новый аудит, поиск референсов и новый макет не требуются.** Предметная основа сохраняется, меняется представление и соответствующие явно запрошенные действия.

## Основа и приоритеты

Основной визуальный образ — [последний макет](../../experiments/placelens-visual/PlaceLens-visual.html), исходники и CSS в том же каталоге. Исполнители обязаны посмотреть его отрисованным, если браузер позволяет, либо изучить сохранённые снимки и исходники. Прочитать HTML как текст недостаточно для заявления о визуальном соответствии. Макет использовать как конкретный образец шрифта, отступов, полей, кнопок, цветов и плотности, а не только как набор функций.

Прямые замечания владельца выше прежних решений макета и пиксельных критериев G4. Исходники проверены: `HomeTripsEditor` прячет общий адрес в details, добавление стоит над списком, `.goal-editor` имеет только нижнюю границу, `.home-orientation-button` малозаметна, первый столбец занимает 34% при паре и 50% при одном адресе, высота карты ограничена 240px/30%. Это наблюдения по коду, не новый браузерный прогон.

Затронут только Новый интерфейс главной. Данные, guards, результаты, API, форматы ссылок, независимость А/Б и защита поздних ответов сохраняются. Выбор адреса остаётся явным; ввод текста не означает подтверждение конкретного объекта. Времена, расстояния, причины отказа и неизвестность не подменяются. Существующие ограничения и источники доступны в подробностях, без постоянного повторения в форме.

Рабочая база содержит незакоммиченные G4.3–G4.5 и документацию приёмки. Перед каждым этапом проверить Git; чужие staged/unstaged/untracked сохранить. Не переключать checkout, не чистить, не коммитить/публиковать без поручения. В начале этапа коротко прочитать актуальный handoff, свой раздел и нужный контракт через [индекс](../README.md), затем выполнять работу.

## U1 — понятный редактор целей и выбор адреса

**Чат 1, Sol 6.1 Medium.** Самый важный этап: пользователь должен самостоятельно добавить три цели без поиска спрятанных действий и поездок вверх-вниз по панели.

### Сделать

- Каждая цель — отдельная визуальная карточка с номером, отступом между карточками, ясной рамкой/фоном. Внутри: короткое название, открытое поле адресного поиска, выбранный адрес/точка, видимое поле ориентира времени с единицей «мин», действие удаления. Общий режим остаётся один для всех целей.
- Адрес цели не прячется в сворачиваемое меню. Источники, координаты, технические подробности и дополнительные действия могут раскрываться отдельно.
- Основной ввод ориентира — непосредственно в карточке с подписью «До … мин»/«Ориентир времени» и пустым необязательным значением. Не заставлять сначала обнаруживать маленькую кнопку и открывать окно. Существующие подробности/живая сводка могут остаться дополнительным действием. Единицы, валидация и снятие понятны; владелец настроек и формулы G4.2a остаются единственными. Не копировать числовые defaults из демо.
- После последней карточки — «Добавить цель»; действие остаётся достижимо там, где закончилось редактирование. Добавление прокручивает к новой карточке и ставит фокус в её первый ввод. Не отправлять к началу списка. На лимите видны `3/3`, без возможности создать четвёртую цель. По возможности сохранить уже введённое название при выборе адреса.
- Счётчик — только `N/3`. Убрать повторные предложения о том, что поездки считаются от каждого адреса. Один понятный запуск расчёта не перекрывает карточки/добавление.
- Различить запрос и выбор: после подтверждения конкретного объекта явно показан выбранный адрес и состояние «Адрес выбран». Если нужна конкретизация корпуса/здания — видимый выбор, до него адрес не объявляется подтверждённым. Для выбранной на карте точки — «Точка выбрана», без выдуманного адресного ID. Не полагаться только на результат обратной подписи, чтобы сообщить об успешном выборе.
- Восстановить пространственную обратную связь поиска: выбор подсказки/объекта приближает общую карту к соответствующему месту. Для найденных групп/клавиатурного предпросмотра можно показать кандидатов, не подтверждая их автоматически. Поиск жилья А/Б и поиск цели должны одинаково понятно связываться с картой. Сам ввод произвольного текста не выбирает случайный первый объект.
- Приближение после явного выбора — разрешённая команда камеры. Это дополнение к прежнему ограничению автоматического fit, а не разрешение двигать камеру от любого ответа. Поздний ответ, правка ориентира и смена вкладки не перехватывают камеру. На телефоне сохранять понятный текущий экран, не уводить из ввода при каждой букве.

**Файлы:** HomeTripsEditor, HomeOrientationButton/контекст ориентиров по необходимости, TripPointPicker/AddressSearch/AddressPicker, HomePage и map handle для явного фокуса. При изменении общего picker сохранить прежних потребителей; новый вариант редактора допустим, новый loader/state результатов — нет.

**Готово:** в рабочем приложении добавить последовательно «Работа», «Школа», третью цель: название → открытый адрес → явный выбор → необязательный ориентир → добавление следующей внизу. Видно границы каждой цели и подтверждённый адрес. Карта приближается к выбранному объекту/цели; ошибочный ввод не выглядит выбранным адресом. Данные и введённые настройки сохраняются.

**Проверки:** typecheck, целевые состояния выбора/ориентиров; один новый browser-проход трёх целей, неоднозначного адреса, фокуса новой карточки и явного приближения. Проверить на 1440×900 и 390×844; короткий экран — при риске недоступного действия. Не повторять весь исторический suite из-за верстки карточек. Показать заполненный редактор и сравнение его стиля с макетом.

## U2 — высота карты и сворачиваемая боковая панель

**Чат 2, Sol 6.1 Medium. Зависимость: U1.** Слово «расширить» трактуется как увеличение высоты карты: владелец сразу просит регулировать её по высоте.

- На обычном desktop сделать карту примерно вдвое выше нынешней, ориентир — около 480px вместо 240px при достаточной высоте окна. На низком ноутбуке разумно ограничить размер, сохранить доступ к результату и возможность регулировки. Не прятать таблицу целиком как единственный способ увеличить карту.
- Между картой и результатами — заметная ручка изменения высоты перетаскиванием. Добавить клавиатурное управление, корректные минимумы/максимумы и сброс размера. Во время drag не выделять текст и не запускать выбор точки карты. Не выполнять аналитические запросы.
- Desktop-боковую панель можно свернуть явной кнопкой и вернуть обратно из постоянно доступного места. Освободившаяся ширина достаётся карте и результату. Сворачивание не уничтожает формы, запросы, настройки и фокус; скрытое содержимое не доступно по Tab. На телефоне сохранить существующий экран «Настройки» без второй конкурирующей навигации.
- Resize контейнера обновляет тот же MapLibre, сохраняет центр/zoom и результаты. Действия поиска из U1 продолжают приближать к явно выбранному месту. Существующее раскрытие карты не должно спорить с ручным размером: определить понятное возвращение к предыдущей высоте.
- Новые размеры можно хранить в памяти страницы. Не добавлять аккаунты, backend или новую схему URL ради размеров.

**Файлы:** HomePage, home-workspace.css, HomeWorkspaceMap; существующие resize-компоненты/хелперы использовать, если подходят, без универсального layout framework.

**Готово:** одновременно видны большая карта и начало результата; пользователь двигает границу, сворачивает и возвращает панель. Ввод, геометрия и камера не теряются. В 1280×560 элементы управления остаются достижимыми. Прежнее требование «три цели и первая строка окружения всегда в первом экране» больше не является критерием: приоритет владельца — более высокая регулируемая карта.

**Проверки:** typecheck, целевой browser resize/collapse/restore с неизменностью камеры и POST, мышь и клавиатура, 1440×900/1280×560 и переход desktop/mobile. Показать карту до/после регулировки и свёрнутую панель.

## U3 — таблица, короткие тексты и единая стилистика

**Чат 3, Sol 6.1 Medium. Зависимость: U2.** Не придумывать новую тему; привести рабочий интерфейс к образцу макета и завершить согласованность компонентов U1–U2.

- Desktop: начальную ширину первой колонки уменьшить приблизительно вдвое: при паре около 17% вместо 34%, освободившееся место — значениям А/Б. Для одиночного профиля тоже уменьшить нынешние 50%. Длинные названия переносятся, не теряются; на 320/390px использовать читаемые минимумы, а не механические 17% в ущерб смыслу.
- Сделать границы колонок регулируемыми по ширине через ручки в заголовке, с клавиатурой и сбросом. Регулируются реальные колонки общей таблицы, значения А/Б не перемешиваются. Не добавлять библиотеку таблиц ради этой задачи. Управление не должно мешать кнопкам заголовка, выделению строки и сортировке, если она существует. При смене одного/двух адресов и viewport корректно ограничивать размеры.
- Убрать повторяющиеся постоянные тексты о данных, источниках и устройстве расчёта из редактора и обычных ячеек. Для авто использовать предложенный владельцем короткий текст «Время без учёта пробок». Для пешего — короткое «По выбранным улицам»; полная оговорка подходов остаётся доступна в ⓘ/подробностях. Это смена уровня подачи, не удаление метода из данных.
- Оставить счётчик целей, убрать длинную расшифровку общего расчёта и дубли сводки. Не занимать отдельные постоянные строки служебными подписями. Убрать визуальное повторение «Данные» там, где оно не помогает действию. Раздел источников/подробностей сохраняется.
- Не скрывать действительную ошибку, неподтверждённый выбор или неизвестное значение: это информация о конкретном результате, не общий методический шум. Не превращать краткость в ложное подтверждение результата. Предупреждение о составе личной ссылки достаточно в её действии; оно не должно повторяться вокруг каждой цели.
- Одна типографика Golos Text, единые поля/кнопки/радиусы/отступы и состояния. Режим и radius выглядят как сегменты макета; основные действия имеют один акцент. Устранить конкурирующие зелёные/фиолетовые стили Нового интерфейса и накопленные перекрывающие правила. А/Б, статусы и числовые значения сохраняют свой смысл. Старый интерфейс не перерисовывать.
- Убрать интерфейсные объяснения внутреннего устройства («общие цели А/Б» в нескольких местах, технические координаты/привязки в обычном состоянии) в дополнительные сведения. Обычная карточка отвечает: куда едем, какой адрес выбран, какой ориентир, что сделать дальше.

**Файлы:** HomeAddressResults/ячейки, стили Нового интерфейса, редактор целей и общие оболочки по необходимости. Не ломать native table, доступные вкладки и возврат к ячейке ради внешнего вида.

**Готово:** первая колонка заметно уже, границы двигаются, числа читаются. Экран рядом с макетом выглядит одной системой: поля, карточки и кнопки не принадлежат разным темам. Постоянный текст минимален, источники и полные ограничения открываются при необходимости. Новый интерфейс узнаваем на реальных состояниях, не только на пустой форме.

**Проверки:** typecheck, целевые регрессии колоночной раскладки/keyboard resize, отсутствия потери названий и источников, 1440×900/1280×720/390×844/320×740. Проверить U1 и U2 на собранном экране. Показать заполненный desktop и телефон рядом с референсом; не объявлять хороший дизайн только по числу passed.

## U4 — короткая приёмка по действиям владельца

**Чат 4, Sol 6.1 Medium. Зависимость: U3.** Проверяет стабильную сборку, найденные дефекты описывает; приложение сам не исправляет. Не повторяет всю G4.6 автоматически.

Основные задания без подсказок:

1. Добавить три разные цели, адрес и ориентир каждой. Для следующей не прокручивать к началу; не раскрывать скрытое основное поле. Видно, выбран ли объект и какая цель редактируется.
2. Выбрать адрес жилья/цели из выдачи: карта приближается к правильному месту; неоднозначность не подтверждается сама, старый ответ не двигает карту.
3. Увеличить/уменьшить высоту карты, свернуть и вернуть панель, изменить ширины колонок. Ввод, результаты, камера и фокус сохранены, лишних POST нет.
4. Сопоставить заполненный экран с макетом: единые элементы, отдельные карточки, мало служебного текста; источники/ограничения доступны по запросу.
5. Пройти расчёт, один отказ/повтор и возврат с карты на 390×844; проверить низкий desktop 1280×560 и узкий 320×740. На 1440×900 оценить большую карту. Проверить переход через breakpoint.

Проверять фактические размеры и отрисовку, не только DOM-текст. Итог — выполненные действия, конкретные дефекты и снимки. При отсутствии препятствий передать владельцу для оценки: он принимает UX. Техническая приёмка не подменяет его отзыв. Источники, GIS/OSRM/ORS и физическое устройство не объявляются проверенными по синтетическим fixtures.

## Экономный порядок работы и handoff

**U1 → U2 → U3 → U4**, последовательно в одном checkout. Ведущий каждого чата — не выше Sol 6.1 Medium. Не создавать субагентов ради формального соблюдения процесса; по умолчанию работать без них. Модели выше потолка не использовать и не рекомендовать как условие успеха.

Один чат = один видимый результат. Не выделять отдельные чаты на аудит, планирование компонентов, мелкие CSS-правки или подготовку handoff. Не переизобретать библиотеки, fixtures, систему дизайна и универсальные абстракции. Типовые технические решения исполнитель принимает сам.

В каждом этапе читать только нужный контекст. Проверки — по [testing](../testing.md), Node в Compose `node` пользователем `node`. Первым делом использовать существующие suites; добавлять тесты только на новое содержательное поведение. Полный browser suite не обязателен после каждого этапа: запускать при изменении общей границы или выявленном риске; ошибки исправлять и повторять затронутые сценарии. Существенные общие регрессии не пропускать ради экономии.

Для visual evidence можно использовать синтетические API существующего стенда с настоящими Vue/MapLibre; синтетика не должна скрывать неудобство полей и отсутствие выбора. Проверка локального приложения с реальными публичными адресами полезна при наличии доступного окружения; не запускать импорты/подготовку routing ради неё. Не менять .env/volumes, зависимости или production assets.

После каждого этапа: короткий handoff в этом плане — файлы/границы, выполненное, команды/результаты, 1–3 ссылки на снимки и нерешённое. В итоговом сообщении показать заполненный экран, а не только список тестов. Не создавать отдельный большой отчёт на каждую правку. Исправление owner feedback не объявлять завершённым до его оценки.

После docs-правок — `scripts/check-docs` без исключений и `git diff --check`. Известную ошибку размера старого interface-v2-plan и прежние WARN отделять от новых. Этот новый план держать до 40 KiB, старую историю не удалять попутно. Текущие контракты и changelog обновлять по фактическим изменениям при реализации, не выдавать план за уже существующее поведение.

### Шаблон запуска каждого чата

«Выполни U.N из docs/plans/interface-usability-corrections.md. Модель Sol 6.1 Medium, без субагентов. Сохрани существующую работу, используй последний макет и прямые замечания владельца. Сделай видимый результат на заполненном приложении, проверь затронутые сценарии и запиши короткий handoff. Следующий этап не начинай».
