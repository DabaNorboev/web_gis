# PlaceLens: правила работы

## Контекст

PlaceLens помогает сравнивать выбранные места в Красноярске по локальным данным и готовиться к проверке условий на месте. Продуктовые границы — [docs/product.md](docs/product.md), устройство — [docs/architecture.md](docs/architecture.md), карта документации — [docs/README.md](docs/README.md).

## Начало и границы задания

- Перед изменениями проверить ветку, HEAD, staged/unstaged и untracked. Не считать untracked-файлы мусором; сохранять постороннюю незавершённую работу.
- Выполнять согласованное задание вместе с необходимыми проверками и исправлениями. Roadmap, исследовательские рекомендации и вложенные материалы сами по себе не разрешают переход к новому продуктовому этапу.
- Не выполнять очистку, изменение рабочих данных, публикацию или операции отката Git как побочный эффект другого задания.
- Не перезаписывать существующие `.env`, ключи и volumes. Импорты, миграции и подготовку геоданных выполнять только в рамках соответствующего задания; заранее установить целевое окружение.
- Не читать и не публиковать секреты, личные координаты, ссылки и тела запросов без необходимости задачи. Диагностика приватности использует синтетические значения.
- `data/reports` может содержать входы подготовки runtime и исторический код. Ignored, generated и большой размер не означают возможность удаления.

## Код и окружение

- Laravel/PHP — API и бизнес-логика, PostGIS — пространственные запросы, Vue/TypeScript — UI, Python — офлайн-подготовка при реальной необходимости. Тяжёлая GIS/raster-обработка внутри HTTP запрещена.
- Базовая аналитика работает без внешних аналитических API; подложка может требовать интернет. Отказ дополнительного источника не скрывает локальные результаты.
- Базовый Compose: nginx/php/node/db. Существующий локальный car pilot подключён routing override; запуск описан в [README](README.md). Не добавлять сервисы заранее.
- Node-команды выполнять в `node` от пользователя `node`, без `--host` для Vite. TypeScript 6 совместим с текущим vue-tsc; не переходить на TS 7 попутно.
- Frontend: [docs/frontend-structure.md](docs/frontend-structure.md). Контроллеры делегируют валидацию и предметные операции; GIS не переносится в UI.
- Разделять ответственность по поведению. Не создавать универсальные абстракции ради удаления нескольких похожих строк и не дробить файлы по формальному лимиту строк.

## Данные и пользовательские обещания

- Выбор конкретного объекта явный. Точка карты не получает выдуманный адресный ID; текстовая группа не считается постоянным ID места.
- Неизвестное значение — `null` с причиной, не ноль. Метод, доступность и актуальность независимы; неизвестная дата наблюдения не заменяется датой публикации, импорта или расчёта.
- Сохранять происхождение, связь со снимком и ограничения покрытия. Geometry/обмен — EPSG:4326, `lon, lat`; расстояния — метры через geography/документированную проекцию, площади — EPSG:32646. Подробности — [схема](docs/data-schema.md), [покрытие](docs/coverage.md), [методика площадей](docs/area-analysis.md).
- Официальные остановки не подмешиваются автоматически из OSM. Парк и растительная территория — независимые признаки; наложенные площади не складываются.
- Близость дороги не доказывает шум/загрязнение, близость парка — доступ, точка контура — вход. Единого субъективного рейтинга и автоматического победителя нет.
- Поездки — ограниченный автомобильный пилот. Не обходить проверки доступа/геометрии, не увеличивать пороги привязки ради успехов, не выдавать модельное время за обычное городское. Контракт — [docs/trips.md](docs/trips.md).

## Проверки и документация

- Выбирать проверки по изменению: [docs/testing.md](docs/testing.md). Изучать scripts перед запуском; учитывать запись кэша, сборки и отчётов.
- GIS-тесты — только через существующую защиту `web_gis_test`; не отключать guards и не использовать рабочую БД.
- Сохранять регрессии доступа, приватности, геометрии, поздних ответов, независимости результатов и истории. Сокращать дублирование стендов, а не защиту из-за количества тестов.
- В итоговом сообщении указывать изменение, выполненные проверки и ограничения. Не представлять прошлые отчёты как сегодняшний успешный запуск.
- У каждого правила/контракта одно основное место. При изменении поведения обновлять его текущий документ; в AGENTS оставлять устойчивые инструкции и ссылки.
- Планы, гипотезы и исторические протоколы имеют явный статус. Не создавать новый отчёт на каждую мелкую правку без потребности; существующие свидетельства и входы воспроизведения сохранять.
